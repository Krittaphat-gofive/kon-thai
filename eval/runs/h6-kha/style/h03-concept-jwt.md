ตอบสั้น ๆ คือเป็นการแลกกันระหว่างความปลอดภัยกับความสะดวกค่ะ access token อายุสั้นเพื่อจำกัดความเสียหายตอนหลุด ส่วน refresh token อายุยาวเพื่อไม่ให้ user ต้อง login ใหม่ทุก 15 นาที

## แต่ละตัวทำหน้าที่อะไร

**access token** คือใบที่แนบไปกับทุก request (`Authorization: Bearer ...`) server แค่ verify signature ก็รู้ว่าเป็นใครมีสิทธิ์อะไร ไม่ต้องยิง DB เลย อายุสั้นมาก ปกติ 5 ถึง 30 นาที

**refresh token** ไม่ได้ใช้เข้าถึง resource ใช้ได้อย่างเดียวคือยิงไปที่ endpoint `/refresh` เพื่อขอ access token ใบใหม่ อายุยาว เป็นวันหรือเป็นสัปดาห์ และเก็บไว้ใน DB หรือ Redis ฝั่ง server ด้วย

## ทำไมไม่ใช้ตัวเดียว

ลองคิดดูทั้งสองทาง

ถ้ามี access token ตัวเดียวแล้วตั้งอายุยาว 7 วัน ปัญหาคือ JWT เป็น stateless ใครก็ตามที่ขโมยใบนี้ไปได้จะใช้งานได้จนครบ 7 วัน และเราสั่ง revoke ไม่ได้ เพราะ server ไม่ได้จำว่าออกใบไหนไปบ้าง ตรวจแค่ลายเซ็นกับวันหมดอายุที่อยู่ในตัว token เอง จะ revoke จริง ๆ ก็ต้องทำ blacklist ซึ่งเท่ากับยิง DB ทุก request เสียความเป็น stateless ไปหมด

ถ้าตั้งอายุสั้น 15 นาทีแล้วไม่มี refresh token ก็ปลอดภัยขึ้น แต่ user ต้องกรอก password ใหม่ทุก 15 นาที ไม่มีใครทนใช้

แยกสองใบแล้วได้ทั้งคู่
- access token หลุด ใช้ได้แค่ไม่กี่นาทีก็หมดอายุ
- refresh token หลุด เรา revoke ได้ทันทีเพราะเก็บ state ไว้ที่ server อยู่แล้ว และการเช็ก DB ตอน refresh เกิดแค่ 15 นาทีครั้ง ไม่ใช่ทุก request

## flow การทำงาน

1. login ผ่าน server ออกให้สองใบ
2. client แนบ access token ไปทุก request
3. พอหมดอายุ server ตอบ 401 กลับมา
4. client ยิง refresh token ไปที่ `/refresh` ขอใบใหม่
5. server เช็กใน store ว่าใบนี้ยังใช้ได้อยู่ไหม ถ้าผ่านก็ออก access token ใบใหม่ให้
6. refresh token หมดอายุหรือโดน revoke เมื่อไหร่ ค่อยเด้งไปหน้า login

ขั้นตอนที่ 3 ถึง 5 ทำเบื้องหลังผ่าน interceptor ได้ user ไม่รู้สึกอะไรเลย

## จุดที่พลาดกันบ่อยตอน implement

- **ไม่เก็บ refresh token ไว้ที่ server** ถ้าออกเป็น JWT ลอย ๆ แล้วเช็กแค่ signature ก็ revoke ไม่ได้อยู่ดี เท่ากับเสียเหตุผลหลักของการมีสองใบไป
- **เก็บ refresh token ใน localStorage** ถ้าโดน XSS สคริปต์อ่านไปได้เลย ใส่ใน httpOnly + Secure + SameSite cookie ปลอดภัยกว่าเพราะ JS อ่านไม่ได้
- **ไม่ทำ rotation** ควรออก refresh token ใบใหม่ทุกครั้งที่ refresh แล้ว invalidate ใบเก่า ถ้าวันไหนเจอใบเก่าโผล่มาใช้ซ้ำ แปลว่ามีคนก๊อปไป ให้ revoke ทั้งสายของ user คนนั้นทิ้ง
- **ใส่ข้อมูลอ่อนไหวใน payload** JWT แค่ encode base64 ไม่ได้เข้ารหัส ใครเอาไปแปะใน jwt.io ก็อ่านได้หมด ใส่แค่ user id กับ role พอ
