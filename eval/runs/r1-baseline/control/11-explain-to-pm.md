ขอสรุปเป็นของที่เอาไปใช้ตอบได้เลยนะ — แบ่งเป็น 3 ส่วน: ประโยคเปิด, อุปมาที่คนไม่ใช่ dev เห็นภาพ, และตาราง breakdown

---

## 1. ประโยคเปิด (ตอบสั้นๆ ก่อน)

> "ปุ่มคือส่วนที่ตามองเห็น แต่สิ่งที่ปุ่มไปสั่งงานข้างหลังมี 3 ชั้น — ตัวปุ่ม, ตัวกลางที่รับคำสั่ง (API), และที่เก็บข้อมูล (database) งานนี้แตะครบทั้ง 3 ชั้น ตัวปุ่มจริงๆ ใช้เวลาไม่ถึงชั่วโมง ที่เหลือคือชั้นที่มองไม่เห็น"

ประโยคสุดท้ายสำคัญ — มันบอกว่าเราไม่ได้อู้ 3 วันกับการวาดปุ่ม

---

## 2. อุปมาที่ใช้ได้ผล

**ย้ายสวิตช์ไฟในบ้าน**

สิ่งที่เห็น คือสวิตช์บนผนัง ดูเหมือนแค่ไขน็อต 2 ตัว
สิ่งที่ต้องทำจริง คือเดินสายใหม่ในผนัง → ไปแก้ที่ตู้เบรกเกอร์ → แล้วต้องไล่เช็กทุกห้องว่าเปิด-ปิดแล้วไฟห้องอื่นไม่ดับตาม

อุปมานี้ดีตรงที่มันสื่อประเด็นหลักได้ว่า **ของเดิมที่ใช้งานอยู่ต้องไม่พัง** ซึ่งเป็นที่มาของเวลาส่วนใหญ่

ถ้า PM ชอบสายธุรกิจมากกว่า ใช้อันนี้: เปลี่ยนชื่อเมนูในเล่มใช้ 5 นาที แต่ถ้าเมนูใหม่ต้องใช้วัตถุดิบใหม่ ก็ต้องหาซัพพลายเออร์ สอนครัว แล้วลองทำให้ชิมก่อนเปิดขายจริง

---

## 3. ตาราง breakdown (อันนี้คือตัวเปลี่ยนเกม)

| วัน | งาน | อธิบายเป็นภาษาคน |
|---|---|---|
| 1 | DB migration | เปลี่ยนโครงสร้างตู้เก็บเอกสาร แล้วย้ายเอกสารเก่าทั้งหมดเข้าช่องใหม่ **โดยห้ามมีแผ่นไหนหาย** ต้องเขียนแผนถอยกลับเผื่อพลาดด้วย เพราะทำกับข้อมูลลูกค้าจริง |
| 2 | API | แก้ "พนักงานรับออเดอร์" ให้รับคำสั่งแบบใหม่ได้ โดยที่คนเดิมที่ยังสั่งแบบเก่าอยู่ (แอปมือถือ, หน้ารายงาน, ระบบที่เชื่อมกับเรา) ยังสั่งได้เหมือนเดิม |
| 3 | Test + review + deploy | ไล่เช็กว่าไม่ไปทำของเดิมพัง + ให้เพื่อนในทีมตรวจโค้ด + ขึ้นระบบจริง |

พอเห็นเป็นตาราง บทสนทนาจะเปลี่ยนจาก *"ทำไมช้า"* เป็น *"ตรงไหนตัดได้บ้าง"* ซึ่งคุยกันง่ายกว่าเยอะ

---

## 4. เตรียมคำตอบไว้ด้วย ถ้าเขาถามต่อว่า "ลัดได้ไหม"

อย่าตอบว่าไม่ได้เฉยๆ — เสนอเป็นทางเลือกพร้อมราคา:

- **ครึ่งวัน** — ทำเฉพาะหน้าบ้าน ปุ่มกดได้ แต่ข้อมูลยังไม่ถูกเก็บจริง เหมาะถ้าต้องการแค่เดโมให้ลูกค้าดู แต่ต้องกลับมาทำให้ครบอยู่ดี
- **2 วัน** — ตัด test อัตโนมัติออก เทสต์ด้วยมือแทน เร็วขึ้นแต่ความเสี่ยงย้ายไปตกที่ production
- **3 วัน** — ทำครบ ขึ้นแล้วจบ

ให้ PM เลือกเอง เพราะการรับความเสี่ยงเป็นการตัดสินใจเชิงธุรกิจ ไม่ใช่เชิงเทคนิค

---

ข้อสังเกตเพิ่ม: ถ้าคำถามแบบนี้เกิดบ่อย ลองเปลี่ยนวิธี estimate ตั้งแต่ต้น — แทนที่จะบอก "3 วัน" ให้บอก "UI ครึ่งวัน, API 1 วัน, migration 1 วัน, test ครึ่งวัน" ตั้งแต่ตอนรับงาน ส่วนใหญ่คำถามจะไม่เกิดเลย
