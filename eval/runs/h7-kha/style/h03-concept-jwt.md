แยกกันเพราะมีสองอย่างที่ขัดกันเองค่ะ token ที่หลุดแล้วเสียหายน้อยต้องอายุสั้น แต่ token อายุสั้นก็ทำให้ user ต้อง login ใหม่บ่อย เลยใช้สองใบแบ่งหน้าที่กัน

## access token

- แนบไปกับทุก request ที่เรียก API ผ่าน header `Authorization: Bearer ...`
- อายุสั้น ปกติ 5 ถึง 15 นาที
- server แค่ verify signature กับวันหมดอายุก็พอ ไม่ต้องยิง database ทุก request ซึ่งเป็นข้อดีหลักของ JWT
- ข้อแลกเปลี่ยนคือยกเลิกกลางคันไม่ได้ ออกไปแล้วใช้ได้จนกว่าจะหมดอายุ เพราะ server ไม่ได้จำว่าเคยออกใบไหนไปบ้าง

## refresh token

- ใช้ขอ access token ใบใหม่อย่างเดียว เรียก API อื่นไม่ได้
- อายุยาว เป็นวันหรือเป็นสัปดาห์
- ส่งไปแค่ endpoint เดียว เช่น `POST /auth/refresh` เลยวิ่งบน network น้อยกว่า access token มาก โอกาสหลุดจากการดักกลางทางหรือ log ก็น้อยกว่า
- เก็บไว้ฝั่ง server ได้ (database หรือ Redis) เลยยกเลิกทีละใบได้จริง

## ทำไมถึงไม่ใช้ใบเดียว

ลองคิดว่ามีใบเดียวทั้งสองกรณี

- ใบเดียวอายุสั้น: ปลอดภัยดี แต่ user ต้อง login ใหม่ทุก 15 นาที ไม่มีใครทน
- ใบเดียวอายุยาว: ใช้สบาย แต่หลุดเมื่อไหร่คนที่ได้ไปก็ใช้ได้ยาว กด logout ฝั่ง client ก็ไม่หยุด เพราะ server ตรวจแค่ลายเซ็นโดยไม่ได้ถามใคร

พอแยกเป็นสองใบ ตัวที่วิ่งบ่อยจะอายุสั้น ส่วนตัวที่อายุยาวจะวิ่งน้อยและคุมได้จาก server

## flow ปกติ

1. login สำเร็จ ได้ทั้ง access token กับ refresh token
2. เรียก API ด้วย access token
3. พอหมดอายุ server ตอบ 401
4. client ยิง `/auth/refresh` พร้อม refresh token แล้วได้ access token ใบใหม่ โดย user ไม่รู้ตัว
5. refresh token หมดอายุหรือโดนยกเลิกเมื่อไหร่ ถึงค่อยเด้งไปหน้า login

## refresh token rotation

ทุกครั้งที่ refresh ให้ออก refresh token ใบใหม่แล้วทิ้งใบเก่า ถ้าวันหลังมีคนเอาใบเก่าที่ทิ้งไปแล้วมาใช้ แปลว่า token ชุดนั้นรั่ว ให้ยกเลิกทั้ง session (เรียกว่า reuse detection) อันนี้คือเหตุผลที่ต้องเก็บ refresh token ไว้ฝั่ง server

## เก็บที่ไหน (ฝั่ง web)

- refresh token: httpOnly + Secure + SameSite cookie เพื่อให้ JavaScript อ่านไม่ได้ กัน XSS ขโมยไป
- access token: เก็บใน memory ของ app หลีกเลี่ยง localStorage เพราะอ่านได้ด้วย script

## จุดที่เจอพลาดบ่อย

- ตั้งอายุ access token เป็นวัน แบบนี้เสียเหตุผลที่แยกสองใบไปเลย
- แนบ refresh token ไปกับทุก request เท่ากับมีใบเดียวอายุยาว
- ไม่เก็บ refresh token ฝั่ง server เลยไม่มีทาง revoke ตอน user เปลี่ยนรหัสผ่านหรือกด logout ทุกอุปกรณ์
- ยัดข้อมูลอ่อนไหวลง payload ของ JWT เพราะ payload เป็นแค่ base64 ใครได้ token ไปก็อ่านได้ ลายเซ็นกันแค่การแก้ไข ไม่ได้ปกปิดเนื้อหา
