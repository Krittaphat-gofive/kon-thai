เกลาแล้วครับ linter เหลือจุดเดียวคือ "รอดำเนินการ" ซึ่งเป็นชื่อสถานะในหน้าจอจริง ไม่ใช่ภาษาราชการที่ต้องแก้

-----

ไดเรกทอรีงานว่างเปล่า ผมเลยยังไม่เห็นโค้ดระบบ HR ขออธิบาย CQRS ให้ก่อนครับ แล้วค่อยให้เกณฑ์ตัดสินว่าเคสไหนคุ้ม/ไม่คุ้ม พร้อมคำถามที่ต้องรู้เพื่อฟันธงได้จริง

## CQRS คืออะไร

**Command Query Responsibility Segregation** = แยก "ทางเขียน" กับ "ทางอ่าน" ออกจากกันเป็นคนละโมเดล

แบบ CRUD ปกติ เราใช้โมเดลเดียวทำทุกอย่าง ใช้ `Employee` entity ตัวเดียวกันทั้งตอนบันทึก ตอนดึงไปโชว์ ตอนทำรายงาน ปัญหาคือสองฝั่งต้องการคนละอย่าง ฝั่งเขียนอยากได้โมเดลที่รักษา business rule ได้แน่น (เช่น "วันลาคงเหลือห้ามติดลบ") ส่วนฝั่งอ่านแค่อยากได้ข้อมูลแบน ๆ ตรงกับหน้าจอ ไม่ต้อง join 8 ตาราง

CQRS แยกเป็น:
- **Command side**: รับคำสั่ง (`ApproveLeaveRequest`, `AdjustSalary`) → validate → เปลี่ยน state ผ่าน domain model ปกติไม่คืนข้อมูลกลับนอกจาก success/fail
- **Query side**: อ่านจาก read model ที่ปั้นมาเพื่อหน้าจอนั้นโดยเฉพาะ ข้าม domain model ไปเลย ยิง SQL ตรงเข้า view หรือตาราง denormalized ได้

## CQRS มี 3 ระดับ แต่คนมักเหมารวมเป็นอันเดียว

| ระดับ | ทำอะไร | ต้นทุน |
|---|---|---|
| 1. แยกแค่ในโค้ด | แยก `CommandHandler` / `QueryHandler` ใช้ DB เดียวกัน (สไตล์ MediatR) | ต่ำมาก ได้ความชัดเจนของโค้ดฟรี ๆ |
| 2. แยก read model ใน DB เดียวกัน | ทำ materialized view / ตาราง denormalized สำหรับ query หนัก ๆ | ปานกลาง ยังอยู่ใน transaction เดียวกันได้ |
| 3. แยก datastore คนละที่ | เขียนลง Postgres อ่านจาก Elasticsearch/Redis sync ด้วย event | สูง ได้ **eventual consistency** มาเป็นของแถม |

ที่เจ็บคือระดับ 3 เพราะ eventual consistency แปลว่า user กดบันทึกแล้ว refresh อาจยังไม่เห็นข้อมูลใหม่ ใน HR เรื่องนี้พังง่าย เพราะ HR มี flow อนุมัติเยอะ ("ผมอนุมัติไปแล้วทำไมยังขึ้นรอดำเนินการ") ต้องออกแบบ UX รองรับ ไม่ใช่แค่เรื่อง backend

อีกอย่าง: **CQRS ≠ Event Sourcing** สองตัวนี้มักมาคู่กันจนคนเข้าใจผิดว่าต้องใช้ด้วยกัน จริง ๆ แยกกันได้

## ระบบ HR เหมาะไหม

ลักษณะที่ระบบ HR มักเป็น และแปลว่าอะไร:

**เข้าทาง CQRS**
- read-heavy ชัดเจน: org chart, ค้นหาพนักงาน, dashboard, รายงาน ปริมาณอ่านมากกว่าเขียนหลายสิบเท่า
- รายงานกับ payroll ต้อง join หนักและ aggregate ข้าม period พวกนี้ทำ read model แยกแล้วดีขึ้นเห็น ๆ
- ต้องการ audit trail เข้ม (ประวัติปรับเงินเดือน เลื่อนตำแหน่ง โอนย้าย) ตรงนี้ event sourcing เฉพาะ aggregate นั้นน่าสนใจ เพราะ HR ต้องตอบได้ว่า "ณ วันที่ 1 ม.ค. ปีที่แล้ว คนนี้สังกัดแผนกไหน เงินเดือนเท่าไร"

**ไม่เข้าทาง**
- transaction volume ปกติต่ำ พนักงานหลักพันถึงหลักหมื่น ไม่ใช่ระบบ e-commerce ที่ยิงวินาทีละพัน request เหตุผลเรื่อง scale ที่คนมักอ้างเพื่อใช้ CQRS แทบไม่เกิดกับ HR
- หลายส่วนเป็น CRUD ตรง ๆ จริง ๆ เช่น แก้ที่อยู่ แก้เบอร์โทร ตั้งค่า master data ประเภทการลา ทำ CQRS ตรงนี้คือเพิ่มไฟล์ 4 ไฟล์เพื่องานที่ `UPDATE` บรรทัดเดียวจบ
- บาง flow ต้องการ read-after-write ทันที เช่น ยอดวันลาคงเหลือ สถานะอนุมัติ ผลคำนวณ payroll ถ้า eventual consistency เข้ามาตรงนี้คือหายนะ

## คำแนะนำ

**อย่าใช้ทั้งระบบ** ให้ใช้เป็นราย bounded context นี่คือจุดที่โปรเจกต์ส่วนใหญ่พลาด คือตัดสินใจระดับสถาปัตยกรรมทั้งก้อนแทนที่จะเลือกเฉพาะที่มีปัญหาจริง

แนวที่ผมจะทำกับระบบ HR:
1. **ระดับ 1 ทั้งระบบ**: แยก command/query handler ช่วยจัดระเบียบโค้ด ต้นทุนเกือบเป็นศูนย์ ไม่มี eventual consistency เข้ามาเกี่ยว
2. **ระดับ 2 เฉพาะรายงาน/dashboard/search**: ทำ read model แยกตรงที่ query ช้าจริง วัดก่อนค่อยทำ
3. **ระดับ 3 เก็บไว้ก่อน**: จนกว่าจะมีเหตุผลที่วัดได้ เช่น รายงาน lock ตาราง production จนคนลางานไม่ได้
4. **Event sourcing เฉพาะ aggregate ที่ต้องการประวัติ**: employment history, compensation ส่วนอื่นไม่ต้อง

## ขอข้อมูลเพิ่มเพื่อฟันธงให้ชัด

คำตอบข้างบนเป็นกรอบทั่วไป จะชี้เฉพาะเจาะจงได้ต้องรู้:

1. **ตอนนี้เจอปัญหาอะไร**: query ช้า? รายงานทำ DB ตาย? โค้ดรก business logic กระจาย? หรือกำลังจะเขียนใหม่? คำตอบต่างกันคนละเรื่องเลย
2. **stack อะไร**: .NET / Node / Java และใช้ ORM อะไร
3. **ขนาด**: พนักงานกี่คน กี่ tenant concurrent user ช่วง peak (ต้นเดือน/ปิด payroll) ประมาณเท่าไร
4. **ทีมกี่คน** และเคยทำ CQRS มาก่อนไหม ตัวนี้สำคัญพอ ๆ กับเรื่องเทคนิค เพราะ CQRS ที่ทีมไม่คุ้นมักกลายเป็น CRUD ที่มีไฟล์เยอะขึ้นเฉย ๆ

ถ้าชี้ path โค้ดระบบ HR มาให้ได้ ผมอ่านแล้วบอกได้เลยครับว่าจุดไหนควรแยก read model ก่อน

**แก้อะไรไปบ้าง**

- **em dash 20 จุด** ตัดออกหมด แทนด้วยเว้นวรรค, `:` หลังหัวข้อตัวหนา, หรือเชื่อมด้วย "เพราะ"/"เช่น"/"ให้" ตามจังหวะประโยค ภาษาไทยไม่ใช้เครื่องหมายนี้
- **ไม้ยมก 8 จุด** "จริงๆ, แบนๆ, ฟรีๆ, หนักๆ, เห็นๆ, ตรงๆ, พอๆ, เฉยๆ" เว้นวรรคหน้าหลังตามราชบัณฑิตฯ
- **"มัน" แทน it** 2 จุด: "ความต้องการของสองฝั่งมันสวนทางกัน" → "สองฝั่งต้องการคนละอย่าง" (ตัดคำนามปลอม "ความต้องการ" ออกด้วย) และหัวข้อ "มันมี 3 ระดับ" → "CQRS มี 3 ระดับ"
- **"ของคุณ"** แบบ your: "โค้ดระบบ HR ของคุณ" → "โค้ดระบบ HR"
- **เรียงประโยคใหม่** ไม่ใช่แค่สลับคำ เช่น "เราใช้โมเดลเดียวทำทุกอย่าง — `Employee` entity ตัวเดียวกัน ทั้งตอน…" → "เราใช้โมเดลเดียวทำทุกอย่าง ใช้ `Employee` entity ตัวเดียวกันทั้งตอน…" และ "ลักษณะที่ HR มักเป็น และตีความได้ว่า" → "ลักษณะที่ระบบ HR มักเป็น และแปลว่าอะไร"
- **"ถือเป็นการจัดระเบียบโค้ดที่ดี"** → "ช่วยจัดระเบียบโค้ด" ตัด "การ" ที่ทำให้กริยากลายเป็นคำนาม
- **จุลภาคระหว่างวลีไทย** ในรายการ read-after-write เปลี่ยนเป็นเว้นวรรค ส่วนรายการที่มีคำอังกฤษปน (org chart, dashboard) คงจุลภาคไว้
- **ระดับภาษา** เป็นข้อความแชต เลยใส่ "ครับ" ที่ประโยคแรกกับประโยคปิดอย่างละคำ ไม่ใส่ทุกประโยค
- **คงไว้ตามเดิม** โค้ด ชื่อ class ชื่อ method ตาราง ตัวเลข เนื้อหาทุกข้อ และ "รอดำเนินการ" ที่เป็นชื่อสถานะในหน้าจอ
