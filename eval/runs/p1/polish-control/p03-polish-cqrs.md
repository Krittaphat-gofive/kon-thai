เกลาแล้วครับ ปรับเฉพาะสำนวน/การเว้นวรรค เนื้อหา โครงสร้าง และโค้ดคงเดิมทั้งหมด

ไดเรกทอรีที่เปิดอยู่ยังว่าง ผมเลยยังไม่เห็นโค้ดระบบ HR ของคุณ — ขออธิบาย CQRS ให้ก่อน แล้วค่อยให้เกณฑ์ว่าเคสไหนคุ้ม/ไม่คุ้ม ปิดท้ายด้วยข้อมูลที่ต้องรู้เพิ่มถึงจะฟันธงได้จริง

## CQRS คืออะไร

**Command Query Responsibility Segregation** คือการแยกฝั่งเขียนกับฝั่งอ่านออกจากกันเป็นคนละโมเดล

แบบ CRUD ปกติ เราใช้โมเดลเดียวทำทุกอย่าง — `Employee` entity ตัวเดียวกันนี่แหละ ทั้งตอนบันทึก ตอนดึงไปโชว์ ตอนทำรายงาน ปัญหาคือความต้องการของสองฝั่งมันสวนทางกัน ฝั่งเขียนอยากได้โมเดลที่รักษา business rule ได้แน่น (เช่น "วันลาคงเหลือห้ามติดลบ") ส่วนฝั่งอ่านแค่อยากได้ข้อมูลแบนๆ ที่ตรงกับหน้าจอ ไม่ต้อง join 8 ตาราง

CQRS แยกเป็น:
- **Command side** — รับคำสั่ง (`ApproveLeaveRequest`, `AdjustSalary`) → validate → เปลี่ยน state ผ่าน domain model ปกติจะไม่คืนข้อมูลกลับ นอกจากบอกว่าสำเร็จหรือไม่สำเร็จ
- **Query side** — อ่านจาก read model ที่ปั้นมาเพื่อหน้าจอนั้นโดยเฉพาะ ข้าม domain model ไปเลย จะยิง SQL ตรงเข้า view หรือตาราง denormalized ก็ได้

## จริงๆ แล้วมี 3 ระดับ แต่คนมักเหมารวมเป็นอันเดียว

| ระดับ | ทำอะไร | ต้นทุน |
|---|---|---|
| 1. แยกแค่ในโค้ด | แยก `CommandHandler` / `QueryHandler` โดยใช้ DB เดียวกัน (สไตล์ MediatR) | ต่ำมาก ได้ความชัดเจนของโค้ดมาแบบฟรีๆ |
| 2. แยก read model ใน DB เดียวกัน | ทำ materialized view หรือตาราง denormalized ไว้รองรับ query หนักๆ | ปานกลาง ยังอยู่ใน transaction เดียวกันได้ |
| 3. แยก datastore ไปคนละที่ | เขียนลง Postgres อ่านจาก Elasticsearch/Redis แล้ว sync ด้วย event | สูง แถม **eventual consistency** มาให้ด้วย |

ที่เจ็บคือระดับ 3 — eventual consistency แปลว่า user กดบันทึกแล้ว refresh อาจยังไม่เห็นข้อมูลใหม่ ซึ่งใน HR พังง่ายมาก เพราะมี flow อนุมัติเต็มไปหมด ("ผมอนุมัติไปแล้ว ทำไมยังขึ้นว่ารอดำเนินการ") ต้องออกแบบ UX มารองรับด้วย ไม่ใช่เรื่องของ backend อย่างเดียว

อีกเรื่อง: **CQRS ≠ Event Sourcing** สองตัวนี้มักมาคู่กันจนคนเข้าใจผิดว่าต้องใช้ด้วยกันเสมอ จริงๆ แยกกันได้

## ระบบ HR เหมาะไหม

ลองดูลักษณะที่ระบบ HR มักเป็น แล้วตีความได้ประมาณนี้

**เข้าทาง CQRS**
- read-heavy ชัดเจน — org chart, ค้นหาพนักงาน, dashboard, รายงาน ปริมาณอ่านมากกว่าเขียนหลายสิบเท่า
- รายงานกับ payroll ต้อง join หนักและ aggregate ข้าม period — พวกนี้แยก read model ออกมาแล้วดีขึ้นเห็นๆ
- ต้องการ audit trail ที่เข้มงวด (ประวัติปรับเงินเดือน เลื่อนตำแหน่ง โอนย้าย) — ตรงนี้ใช้ event sourcing เฉพาะ aggregate นั้นน่าสนใจ เพราะ HR ต้องตอบให้ได้ว่า "ณ วันที่ 1 ม.ค. ปีที่แล้ว คนนี้สังกัดแผนกไหน เงินเดือนเท่าไร"

**ไม่เข้าทาง**
- ปริมาณ transaction ต่ำอยู่แล้ว พนักงานหลักพันถึงหลักหมื่น ไม่ใช่ระบบ e-commerce ที่โดนยิงวินาทีละพัน request — เหตุผลเรื่อง scale ที่คนมักยกมาอ้างตอนจะใช้ CQRS แทบไม่เกิดกับ HR
- หลายส่วนเป็น CRUD ตรงๆ จริงๆ — แก้ที่อยู่ แก้เบอร์โทร ตั้งค่า master data ประเภทการลา ทำ CQRS ตรงนี้เท่ากับเพิ่มไฟล์ 4 ไฟล์ให้งานที่ `UPDATE` บรรทัดเดียวก็จบ
- บาง flow ต้องการ read-after-write ทันที — ยอดวันลาคงเหลือ, สถานะอนุมัติ, ผลคำนวณ payroll ถ้า eventual consistency โผล่มาตรงนี้คือหายนะ

## คำแนะนำ

**อย่าใช้ทั้งระบบ** — ให้เลือกใช้เป็นราย bounded context จุดที่โปรเจกต์ส่วนใหญ่พลาดคือไปตัดสินใจระดับสถาปัตยกรรมทีเดียวทั้งก้อน แทนที่จะเลือกเฉพาะตรงที่มีปัญหาจริง

ถ้าเป็นผม กับระบบ HR จะทำแบบนี้
1. **ระดับ 1 ทั้งระบบ** — แยก command/query handler ถือเป็นการจัดระเบียบโค้ดที่ดี ต้นทุนแทบเป็นศูนย์ และไม่มีเรื่อง eventual consistency เข้ามาเกี่ยว
2. **ระดับ 2 เฉพาะรายงาน/dashboard/search** — ทำ read model แยกเฉพาะตรงที่ query ช้าจริง วัดก่อนแล้วค่อยทำ
3. **ระดับ 3 เก็บไว้ก่อน** — จนกว่าจะมีเหตุผลที่วัดออกมาเป็นตัวเลขได้ เช่น รายงานไป lock ตาราง production จนคนลางานไม่ได้
4. **Event sourcing เฉพาะ aggregate ที่ต้องการประวัติ** — employment history, compensation ส่วนที่เหลือไม่ต้อง

## ขอข้อมูลเพิ่มเพื่อให้ฟันธงได้ชัดขึ้น

ที่ตอบไปข้างบนเป็นกรอบกว้างๆ ถ้าจะชี้ให้เจาะจงกว่านี้ ขอรู้เพิ่มว่า

1. **ตอนนี้ติดปัญหาอะไรอยู่** — query ช้า? รายงานรันทีทำ DB ตาย? โค้ดรก business logic กระจัดกระจาย? หรือกำลังจะเขียนใหม่? แต่ละข้อคำตอบคนละเรื่องกันเลย
2. **ใช้ stack อะไร** — .NET / Node / Java และใช้ ORM ตัวไหน
3. **ขนาดระบบ** — พนักงานกี่คน กี่ tenant และ concurrent user ช่วง peak (ต้นเดือน / ปิด payroll) ประมาณเท่าไร
4. **ทีมกี่คน** และเคยทำ CQRS มาก่อนไหม — ข้อนี้สำคัญพอๆ กับเรื่องเทคนิค เพราะ CQRS ในทีมที่ไม่คุ้น มักลงเอยเป็น CRUD ที่มีไฟล์เยอะขึ้นเฉยๆ

ถ้าชี้ path ของโค้ดระบบ HR มาได้ ผมอ่านแล้วบอกได้เลยว่าควรแยก read model ตรงไหนก่อน
