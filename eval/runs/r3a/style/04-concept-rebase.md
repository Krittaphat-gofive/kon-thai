ต่างกันที่วิธีรวมงานกับหน้าตาของ history ครับ merge เก็บประวัติไว้ตามจริง ส่วน rebase เขียนประวัติใหม่ให้เป็นเส้นตรง

## merge

เอาปลายของสอง branch มาบรรจบกัน แล้ว git สร้าง merge commit ขึ้นมาหนึ่งก้อน commit เดิมอยู่ครบ hash ไม่เปลี่ยน กราฟจะเห็นชัดว่างานแตกไปตอนไหนและกลับมารวมตอนไหน ข้อเสียคือถ้าทีมใหญ่และ merge กันบ่อย กราฟจะรกจนอ่านไม่ออก

## rebase

ยก commit ของ branch เราไปวางต่อท้าย commit ล่าสุดของ main ทีละก้อน git สร้าง commit ใหม่หมด hash เปลี่ยนทั้งชุด ผลที่ได้คือ history เส้นเดียว `git log` อ่านง่าย แต่ประวัติที่ได้ไม่ตรงกับสิ่งที่เกิดขึ้นจริง

| | merge | rebase |
|---|---|---|
| history | แตกแขนง ตรงตามจริง | เส้นตรง อ่านง่าย |
| hash ของ commit เดิม | คงเดิม | เปลี่ยนใหม่หมด |
| conflict | แก้ครั้งเดียวตอนรวม | แก้ทีละ commit |
| ย้อนกลับทั้งก้อน | revert merge commit ก้อนเดียวจบ | ไล่ revert ทีละก้อน |
| branch ที่ push ไปแล้ว | ปลอดภัย | ต้อง force push |

กฎเหล็กข้อเดียว: อย่า rebase branch ที่คนอื่นดึงไปใช้แล้ว เพราะ hash เปลี่ยนหมด พอเพื่อน pull จะได้ commit ซ้อนกันสองชุดและ history พัง ถ้าจำเป็นต้อง push หลัง rebase ใช้ `--force-with-lease` ไม่ใช่ `--force`

## ทีมควรใช้แบบไหน

ไม่ต้องเลือกข้างใดข้างหนึ่ง สูตรที่ใช้กันเยอะและเวิร์กที่สุดคือผสมสองอย่าง

1. อัปเดต feature branch ของตัวเองจาก main ให้ใช้ rebase เพราะ branch ยังไม่มีใครใช้ ตั้งค่าไว้ครั้งเดียวเลย
   ```
   git config --global pull.rebase true
   ```
2. ตอนเอางานเข้า main ให้ merge ผ่าน PR เสมอ จะได้มีจุดให้ review และ revert ง่าย

ส่วนจะ merge แบบไหนตอนปิด PR เลือกตามลักษณะทีม
- PR เล็ก งานจบใน 1 - 2 วัน: ใช้ squash merge ได้ 1 commit ต่อ 1 PR history สะอาดมาก และหา commit ที่ทำให้พังง่าย
- commit ย่อยมีความหมายจริง ๆ หรือต้อง `git bisect` บ่อย: ใช้ `merge --no-ff` เก็บ commit ย่อยไว้

ถ้าทีมยังไม่เคยคุยเรื่องนี้กัน ผมแนะนำเริ่มจาก rebase ตอน sync กับ squash merge ตอนปิด PR ก่อน เพราะกฎจำง่าย คนใหม่เข้าทีมแล้วทำตามได้ทันที แล้วค่อยปรับทีหลังถ้ารู้สึกว่าอยากเก็บ commit ย่อย

อยากให้ช่วยร่างเป็น git workflow ของทีมพร้อมคำสั่งที่ใช้จริงไหมครับ
