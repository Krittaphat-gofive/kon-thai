CQRS ย่อจาก Command Query Responsibility Segregation แปลง่าย ๆ คือแยกฝั่งที่เปลี่ยนข้อมูล (command) ออกจากฝั่งที่อ่านข้อมูล (query) ให้เป็นคนละ model กันไปเลยครับ

ประเด็นที่คนเข้าใจผิดบ่อยคือคิดว่า CQRS ต้องมีสอง database ความจริงแล้วแยก database เป็นแค่ปลายสุดของสเกล ไม่ใช่ตัว pattern

## CQRS มีสามระดับ

**ระดับ 1: แยกแค่ในโค้ด**
ฝั่งเขียนเป็น `CreateLeaveRequestCommand` ฝั่งอ่านเป็น `GetLeaveBalanceQuery` คนละ class คนละ handler ใช้ database เดียวกัน ถ้า stack เป็น .NET ก็มักทำผ่าน MediatR ระดับนี้แทบไม่มีต้นทุนอะไร ได้ประโยชน์เรื่องความชัดเจนของโค้ดล้วน ๆ

**ระดับ 2: แยก model แต่ database เดียว**
ฝั่งเขียนใช้ entity ที่มี validation และ business rule ครบ ฝั่งอ่าน query ตรงจาก view หรือ dapper เลย ไม่ต้องโหลด entity ทั้งก้อนมา map ประโยชน์คือ query ที่ซับซ้อนทำได้เร็วขึ้นมาก โดยไม่ต้องบิด domain model ให้เพี้ยน

**ระดับ 3: แยก datastore คนละตัว**
ฝั่งเขียนลง SQL ฝั่งอ่านลง Elasticsearch หรือ denormalized table แล้ว sync กันด้วย event ระดับนี้ได้ performance แต่แลกมากับ eventual consistency ผู้ใช้กดบันทึกแล้วอาจยังไม่เห็นข้อมูลใหม่ในหน้า list ทันที

## ราคาที่ต้องจ่าย

| ได้ | เสีย |
|---|---|
| query เร็วขึ้น scale แยกฝั่งได้ | โค้ดเยอะขึ้น 2-3 เท่า |
| business logic ไม่ปนกับ reporting | debug ยากขึ้น ต้องไล่ข้าม handler |
| audit trail ทำง่ายถ้าคู่กับ event sourcing | ระดับ 3 ต้องยอมรับข้อมูลหน่วง |

## แล้วระบบ HR เหมาะไหม

ตอบแบบไม่รู้รายละเอียดระบบ คือ**ระดับ 1-2 คุ้ม ระดับ 3 ส่วนใหญ่ไม่คุ้ม**

เหตุผลคือ HR มีลักษณะเฉพาะที่สวนทางกับ CQRS เต็มรูปแบบ

- traffic ไม่สูง พนักงานพันคนก็ยังไม่ใกล้จุดที่ database ตัวเดียวเอาไม่อยู่ เหตุผลหลักของระดับ 3 คือ scale ซึ่ง HR มักไม่มีปัญหานี้
- consistency สำคัญมาก ยอดวันลาคงเหลือ ยอดเงินเดือน พวกนี้ผิดไม่ได้แม้แต่วินาทีเดียว คนกดลาแล้วรีเฟรชเห็นยอดเดิม จะกลายเป็นเรื่องทันที
- business rule ซับซ้อนกว่าที่คิด การคิดวันลาตามอายุงาน การคำนวณ OT ตามกะ พวกนี้อยู่ฝั่ง command ล้วน ๆ แยก read model ไปก็ไม่ได้ช่วยอะไร

**จุดที่ CQRS ระดับสูงคุ้มใน HR** มีอยู่บ้าง แต่เป็นเฉพาะส่วน ไม่ใช่ทั้งระบบ

- รายงานกับ dashboard ที่ต้อง join ข้ามสิบตาราง แยกเป็น read model หรือ materialized view คุ้มมาก
- ข้อมูล attendance หรือ time log ที่มี record หลักล้าน ถ้าหน้า report ช้า แยก read store ออกมาช่วยได้จริง
- หน้าค้นหาพนักงาน ถ้าต้องค้นแบบ full-text หลายเงื่อนไข ยัดลง search index แยกก็สมเหตุสมผล

**จุดที่ไม่ควรแตะ** คือ leave balance, payroll run, approval flow ทุกอย่างที่คนกดแล้วต้องเห็นผลทันที

## คำแนะนำ

ถ้าตอนนี้ยังไม่ได้ใช้อะไรเลย เริ่มที่ระดับ 1 ก่อน แยก command กับ query ในโค้ด แล้วค่อยยกเฉพาะหน้าที่ช้าจริงขึ้นเป็นระดับ 2-3 ทีละจุด การกระโดดไปทำ event sourcing + read store ทั้งระบบตั้งแต่แรก มักจบด้วยทีมใช้เวลาไปกับ infra มากกว่าฟีเจอร์

อยากให้ชี้ชัดกว่านี้ รบกวนบอกหน่อยครับว่าระบบตอนนี้ขนาดประมาณไหน พนักงานกี่คน แล้วปัญหาที่ทำให้นึกถึง CQRS คืออะไร ช้าตรงหน้าไหน หรือโค้ดเริ่มรก
