สมมติไว้เลยว่ารหัสผ่านนี้หลุดไปแล้วครับ repo เป็น public ตั้งแต่เมื่อวาน แปลว่า bot ที่ไล่ scan GitHub หา secret มีเวลาเก็บไปแล้วเป็นวัน บางตัวเจอภายในไม่กี่นาทีหลัง push ด้วยซ้ำ งานด่วนที่สุดตอนนี้คือเปลี่ยนรหัส ไม่ใช่ลบ commit เพราะลบ commit อย่างเดียวไม่ช่วยอะไรถ้ารหัสเดิมยังใช้ได้อยู่

## ทำตอนนี้เลย ตามลำดับ

1. เปลี่ยนรหัสผ่านของ DB user ตัวนั้น ถ้าทำได้ ให้สร้าง user ใหม่แล้ว disable ตัวเก่าไปเลย จะได้เห็นว่ามีอะไรเรียกใช้ตัวเก่าอยู่บ้าง
2. อัปเดตรหัสใหม่ในที่ที่ระบบใช้งานจริง (environment variable, secret manager, CI/CD) แล้ว deploy
3. ปิดทางเข้าถึงจากข้างนอก เช็กว่า DB เปิดรับ connection จาก public internet อยู่หรือเปล่า ถ้าเปิดอยู่ ให้ตั้ง firewall หรือ IP allowlist ให้เหลือเฉพาะ IP ที่จำเป็น ข้อนี้สำคัญพอ ๆ กับการเปลี่ยนรหัส เพราะต่อให้รหัสหลุด ถ้าต่อเข้ามาไม่ได้ก็ทำอะไรไม่ได้
4. ไล่ดู connection log กับ audit log ของ DB ย้อนไปตั้งแต่เวลาที่ push ดูว่ามี login จาก IP ที่ไม่รู้จักไหม ทั้งที่สำเร็จและไม่สำเร็จ และมี query แปลก ๆ หรือการดึงข้อมูลออกก้อนใหญ่หรือเปล่า เก็บ log ช่วงนี้แยกไว้ก่อน เผื่อต้องใช้ตอนสอบสวน

## แจ้งคนที่เกี่ยวข้อง

บอกหัวหน้าทีมกับคนดูแล security ของบริษัทตั้งแต่ตอนนี้ อย่าเพิ่งเงียบไว้แล้วแก้เอง ถ้า DB ตัวนี้มีข้อมูลส่วนบุคคลของลูกค้า เรื่องนี้อาจเข้าข่ายเหตุละเมิดข้อมูลตาม PDPA ซึ่งมีกรอบเวลาแจ้ง สคส. ภายใน 72 ชั่วโมงนับจากทราบเหตุ การประเมินว่าต้องแจ้งหรือไม่ ปล่อยให้ทีมที่รับผิดชอบตัดสิน

## ค่อยมาล้าง Git history

ทำหลังเปลี่ยนรหัสเรียบร้อยแล้ว ขั้นนี้คือลดโอกาสที่คนอื่นจะไปเจอทีหลัง ไม่ใช่การแก้ปัญหาหลัก

- ลบ secret ออกจาก history ด้วย `git filter-repo` หรือ BFG Repo-Cleaner การ commit ทับใหม่ไม่พอ เพราะค่าเดิมยังอยู่ใน history
- force push ขึ้น remote แล้วบอกทุกคนในทีมให้ clone ใหม่ เพราะ history เปลี่ยนไปทั้งก้อน ถ้าใครยังใช้ของเดิมแล้ว push กลับมา secret จะกลับขึ้นไปอีก
- เช็กว่ามีคน fork ไปหรือยัง fork แต่ละอันมีประวัติเดิมครบ ต้องให้เจ้าของลบเอง
- ติดต่อ GitHub Support ให้ลบ cached view ของ commit เก่า เพราะ commit ที่ไม่มี branch ชี้ถึงแล้วยังเปิดดูได้ผ่าน URL ตรง ๆ
- ถ้า repo นี้ไม่จำเป็นต้อง public ก็พิจารณาเปลี่ยนเป็น private ไปด้วย

## กันไม่ให้เกิดอีก

- ย้าย connection string ออกจากไฟล์ที่ commit ไปอยู่ใน environment variable หรือ secret manager ส่วนไฟล์ที่ commit เก็บแค่ key เปล่า ๆ เช่น `appsettings.Example.json`
- เพิ่มไฟล์ config จริงลง `.gitignore`
- เปิด secret scanning กับ push protection ใน settings ของ repo ตัว push protection จะบล็อกให้ตั้งแต่ตอน push
- ติด pre-commit hook อย่าง gitleaks ไว้ในเครื่อง จะได้เจอก่อนขึ้น remote

ถ้าบอกได้ว่า DB อยู่ที่ไหน (cloud provider หรือ on-prem) กับเปิดรับ connection จากข้างนอกอยู่ไหม เดี๋ยวช่วยดูให้ว่าควรเรียงลำดับยังไงในเคสนี้ครับ
