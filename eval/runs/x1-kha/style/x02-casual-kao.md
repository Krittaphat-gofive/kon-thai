เริ่มจากความคิดเดียวก่อนค่ะ: unit test คือโค้ดที่เรียกฟังก์ชันหนึ่งตัวด้วย input ที่เรารู้คำตอบอยู่แล้ว แล้วเช็กว่าผลลัพธ์ตรงกับที่คาดไว้ไหม แค่นั้นเลย ไม่มีอะไรลึกลับไปกว่านี้

## โครงสร้าง 3 ขั้น

ทุก test เขียนตามลำดับนี้ได้หมด

1. **Arrange** เตรียมข้อมูลที่จะใช้
2. **Act** เรียกฟังก์ชันที่อยากทดสอบ
3. **Assert** เทียบผลที่ได้กับผลที่ควรจะเป็น

## ตัวอย่างจริง

สมมติมีฟังก์ชันนี้อยู่ในไฟล์ `cart.py`

```python
def calculate_discount(price, is_member):
    if price < 0:
        raise ValueError("price must not be negative")
    if is_member and price >= 1000:
        return price * 0.9
    return price
```

สร้างไฟล์ชื่อ `test_cart.py` ไว้ข้าง ๆ กัน

```python
from cart import calculate_discount


def test_member_buying_over_1000_gets_discount():
    # Arrange
    price = 2000

    # Act
    result = calculate_discount(price, is_member=True)

    # Assert
    assert result == 1800
```

ชื่อไฟล์ต้องขึ้นต้นด้วย `test_` และชื่อฟังก์ชันก็ต้องขึ้นต้นด้วย `test_` เหมือนกัน เพราะ pytest ใช้ชื่อนี้ค้นหา test เอง ส่วนชื่อหลัง `test_` เขียนยาวได้เลย ให้อ่านแล้วรู้ว่าเคสนี้ทดสอบอะไร เวลา test แดงจะได้รู้ทันทีว่าพังตรงไหน

รันด้วย

```powershell
pip install pytest
python -m pytest -v
```

## ลองทำให้ fail สักครั้ง

ข้อนี้สำคัญกว่าที่คิด ลองแก้ `1800` เป็น `1700` แล้วรันใหม่ จะเห็น pytest บอกว่าคาดไว้เท่าไหร่ ได้จริงเท่าไหร่

test ที่ผ่านตั้งแต่แรกโดยไม่เคยเห็นมันแดงเลย บางทีก็เป็น test ที่เขียนผิดจนจับอะไรไม่ได้เลย เช่นลืม `assert` ไปเฉย ๆ

## จะทดสอบเคสไหนบ้าง

เวลาเจอฟังก์ชันใหม่ ให้ถามตัวเอง 3 คำถาม

- **เคสปกติ** ใช้งานแบบที่ตั้งใจไว้ ได้ผลถูกไหม
- **เคสขอบ** ค่าตรงรอยต่อของเงื่อนไข ในตัวอย่างนี้คือ 999 กับ 1000 เพราะบั๊กชอบซ่อนตรง `>` กับ `>=`
- **เคสพัง** ใส่ค่าที่ไม่ควรใส่ ฟังก์ชันโวยวายถูกวิธีไหม

พอเคสเริ่มเยอะ จะเขียนซ้ำทีละตัวก็เปลืองแรง ใช้ `parametrize` รวบได้

```python
import pytest

from cart import calculate_discount


@pytest.mark.parametrize("price, is_member, expected", [
    (2000, True, 1800),    # สมาชิก ซื้อเกินเกณฑ์
    (2000, False, 2000),   # ไม่ใช่สมาชิก ไม่ลด
    (1000, True, 900),     # ขอบล่างพอดี ต้องลด
    (999, True, 999),      # ต่ำกว่าขอบ 1 บาท ไม่ลด
])
def test_calculate_discount(price, is_member, expected):
    assert calculate_discount(price, is_member) == expected


def test_negative_price_raises():
    with pytest.raises(ValueError):
        calculate_discount(-1, is_member=True)
```

4 บรรทัดใน list นั้นนับเป็น 4 test แยกกัน ตัวไหนพังก็เห็นชัดว่าตัวไหน

## กับดักที่เจอบ่อยตอนเริ่มใหม่ ๆ

- **assert แบบหลวม ๆ** เขียน `assert result` เฉย ๆ แปลว่าแค่ไม่เป็น 0 หรือ None ก็ผ่านแล้ว ให้เทียบค่าจริงไปเลย
- **test ที่พึ่งของข้างนอก** ถ้าต้องต่อ DB ยิง API หรืออ่านไฟล์จริง มันจะช้าและแดงมั่วตอนเน็ตล่ม ของพวกนี้ค่อยไปเรียน mock ทีหลัง ตอนนี้เริ่มจากฟังก์ชันที่รับค่าเข้า คืนค่าออก ไม่ยุ่งกับอะไรข้างนอก จะง่ายที่สุด
- **test ที่ต้องรันเรียงลำดับ** แต่ละ test ต้องอยู่ได้ด้วยตัวเอง รันตัวเดียวโดด ๆ ก็ต้องผ่าน
- **ยัดหลายเรื่องใน test เดียว** ถ้าชื่อ test ต้องมีคำว่า "and" แปลว่าควรแยกเป็นสองตัว
