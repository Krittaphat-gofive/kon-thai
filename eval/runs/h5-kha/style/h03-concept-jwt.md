แยกกันเพราะสองตัวนี้แลกกันคนละอย่างค่ะ access token ต้องการให้ verify เร็วโดยไม่ต้องแตะ DB แลกมากับการ revoke ไม่ได้ เลยต้องให้อายุสั้น ส่วน refresh token อายุยาวเพื่อไม่ให้ผู้ใช้ login ใหม่ทุก 15 นาที แลกมากับการที่ต้องเก็บใน DB และเช็กทุกครั้งที่ใช้

## ทำไม access token ต้องอายุสั้น

JWT ที่ server verify ด้วย signature อย่างเดียว แปลว่า server ไม่ต้องรู้จัก token ใบนั้นมาก่อนก็บอกได้ว่าของจริง ข้อดีคือ API ทุกตัวตรวจเองได้ ไม่ต้องยิง DB ทุก request ข้อเสียที่ตามมาคือ พอออกไปแล้วจะยกเลิกกลางคันไม่ได้ ต่อให้ user กด logout หรือโดนแบน token ใบนั้นก็ยังผ่าน validation จนกว่าจะหมดอายุ

ถ้าตั้งอายุไว้ 7 วันแล้วมีคนขโมย token ไปจาก localStorage คนนั้นใช้ได้ 7 วันเต็ม ตั้งไว้ 15 นาทีก็จำกัดความเสียหายเหลือ 15 นาที

## แล้วทำไมไม่ให้ login ใหม่ไปเลย

เพราะ UX พัง ทางออกคือออก token ใบที่สองที่มีหน้าที่เดียว: ขอ access token ใบใหม่ เอาไปเรียก API อื่นไม่ได้

refresh token เก็บใน DB ได้ เพราะใช้แค่ 15 นาทีครั้ง ไม่ใช่ทุก request เลยไม่เปลืองเหมือนเช็ก access token ทุกครั้ง พอเก็บใน DB ได้ ก็ลบทิ้งได้ ซึ่งแปลว่า logout ได้จริง ถอนสิทธิ์เครื่องที่หายได้จริง

## flow ที่เกิดขึ้นจริง

```
login            -> ได้ access (15 นาที) + refresh (30 วัน)
เรียก API        -> ส่ง access ไปใน Authorization header
access หมดอายุ   -> API ตอบ 401
                 -> ยิง POST /auth/refresh พร้อม refresh token
                 -> ได้ access ใบใหม่ แล้ว retry request เดิม
refresh หมดอายุ  -> login ใหม่
```

ฝั่ง frontend ปกติทำใน interceptor เจอ 401 ครั้งแรกให้ refresh แล้วยิงซ้ำอัตโนมัติ ผู้ใช้ไม่รู้ตัวว่าเกิดอะไรขึ้น

## อายุที่ใช้กันทั่วไป

| token | อายุ | เก็บที่ไหน |
|---|---|---|
| access | 5 ถึง 15 นาที | ตัวแปรใน memory หรือ sessionStorage |
| refresh | 7 ถึง 30 วัน | httpOnly + Secure cookie |

ที่แนะนำให้ refresh อยู่ใน httpOnly cookie เพราะ JavaScript อ่านไม่ได้ ถ้าโดน XSS สคริปต์จะขโมยไปไม่ได้ แต่ต้องตั้ง `SameSite` กัน CSRF ด้วย ส่วน access token อยู่ใน memory ก็พอ เพราะหายตอน refresh หน้าก็แค่ขอใหม่

## สองเรื่องที่คนมักพลาด

**เก็บข้อมูลเยอะเกินใน access token** payload ของ JWT เป็น base64 ไม่ใช่การเข้ารหัส ใครก็ตามที่ได้ token ไปเอาไปเปิดดูได้หมด ใส่แค่ user id, role, เวลาหมดอายุ อย่าใส่เบอร์โทรหรือเลขบัตร

**refresh token ใช้ซ้ำได้ไม่จำกัด** ควรทำ rotation คือทุกครั้งที่ refresh ให้ออกใบใหม่แล้วยกเลิกใบเก่า ถ้าวันหนึ่งมีคนเอาใบเก่าที่ยกเลิกไปแล้วมาใช้ แปลว่า token รั่ว ให้ลบ refresh token ทั้ง family ของ user คนนั้นทิ้งแล้วบังคับ login ใหม่

ถ้าใช้ stack ไหนอยู่ บอกมาได้ เดี๋ยวเขียนตัวอย่าง endpoint `/auth/refresh` กับส่วน rotation ให้ตรงกับที่ใช้คะ
