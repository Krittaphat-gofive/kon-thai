## Idempotency คืออะไร

สั้น ๆ คือ "ยิงซ้ำกี่รอบ ผลลัพธ์ก็เหมือนเดิม"

ถ้า API ตัวหนึ่ง idempotent แปลว่าเรียกครั้งเดียวกับเรียก 5 ครั้งด้วย request เดิม สถานะในระบบจะจบที่เดิม ไม่ใช่ว่าเงินถูกโอน 5 รอบ

ของที่ idempotent อยู่แล้วตามธรรมชาติ:
- `GET` — อ่านอย่างเดียว
- `PUT /employees/123 {salary: 50000}` — เซ็ตค่าให้เป็น 50000 ยิงกี่ครั้งก็ 50000
- `DELETE /employees/123` — ลบไปแล้วก็ลบแล้ว

ตัวมีปัญหาคือ `POST` แบบ "สร้างใหม่" หรือ "สั่งทำ action":
```
POST /payroll/runs/2026-09/disburse
```
ยิงซ้ำ = จ่ายซ้ำ ถ้าไม่ได้ออกแบบมากัน

## ทำไมระบบจ่ายเงินเดือนต้องแคร์เป็นพิเศษ

เพราะ **network ไม่เคยบอกความจริงทั้งหมด** ปัญหาคลาสสิกคือ client ไม่มีทางแยกออกว่า:

- request ไปไม่ถึง server (ปลอดภัย retry ได้)
- request ถึงแล้ว server ทำงานเสร็จแล้ว แต่ response หายระหว่างทาง / timeout (retry = จ่ายซ้ำ)

ทั้งสองเคสหน้าตาเหมือนกันเป๊ะจากฝั่ง client — เห็นแค่ timeout

ทีนี้ในบริบท payroll มันเจ็บกว่าระบบอื่นตรงที่:

**1. เงินออกแล้วเอาคืนยาก** ระบบ e-commerce ยิงซ้ำแล้วออเดอร์ซ้ำ ลูกค้าโทรมาแจ้ง ยกเลิกได้ แต่โอนเงินเดือนเข้าบัญชีพนักงานเกินไป 1 รอบ ต้องไปตามเก็บคืน ซึ่งเป็นเรื่องทั้ง HR ทั้งกฎหมายแรงงาน ทั้งความรู้สึกคน

**2. งานมันรันเป็น batch ใหญ่** จ่ายพนักงาน 3,000 คนในรอบเดียว ระหว่างนั้นมีโอกาสเจอ timeout, deploy, pod restart, connection reset ได้หมด แล้วคนที่มา retry อาจจะไม่ใช่ระบบด้วยซ้ำ — เป็น HR กดปุ่มซ้ำเพราะหน้าจอค้าง

**3. มันต่อกับระบบนอก** ธนาคาร, payment gateway, ระบบประกันสังคม/ภาษี ตัวกลางพวกนี้มี retry logic ของมันเอง และมักส่ง webhook ซ้ำโดยตั้งใจ (at-least-once delivery) ถ้าฝั่งเรารับ webhook `payment.success` แล้วบันทึกซ้ำ ยอดใน ledger จะเพี้ยนทันที

**4. ตรวจสอบย้อนหลังได้ตลอด** ข้อมูลเงินเดือนโดน audit โดนตรวจสอบภาษี ถ้า record ซ้ำหรือยอดไม่ match กับ statement ธนาคาร งานตามแก้จะบานปลาย

## ทำยังไง

**Idempotency key** — ให้ client ส่ง key ที่ unique ต่อ "เจตนา" หนึ่งครั้งมาด้วย

```http
POST /payroll/runs/2026-09/disburse
Idempotency-Key: payroll-2026-09-run-01
```

ฝั่ง server:
1. เอา key ไป insert ลงตาราง `idempotency_records` โดยมี unique constraint
2. ถ้า insert ไม่ผ่าน (key ซ้ำ) = เคยทำไปแล้ว → คืน response เดิมที่เก็บไว้ ไม่ทำงานซ้ำ
3. ถ้าผ่าน = ของใหม่ → ทำงานจริง แล้วเก็บ response ไว้คู่กับ key

จุดสำคัญคือต้องให้ "การจอง key" กับ "การทำงานจริง" อยู่ใน transaction เดียวกัน ไม่งั้นจะมีช่องว่างที่ request สองตัวเข้ามาพร้อมกันแล้วผ่านทั้งคู่

เรื่องที่คนมักพลาด:
- **key ต้องมาจาก client ไม่ใช่ server generate** ถ้า server สุ่มให้ ยิงซ้ำก็ได้ key ใหม่ ไม่มีประโยชน์
- **key ต้องผูกกับความหมายทางธุรกิจ** เช่น `{payroll_run_id}:{employee_id}` ไม่ใช่ UUID สุ่มที่ client สร้างใหม่ทุกครั้งที่กดปุ่ม — ไม่งั้น HR กดสองครั้งก็ยังจ่ายซ้ำอยู่ดี
- **ต้องเช็กด้วยว่า payload ที่มากับ key เดิมเหมือนเดิมไหม** ถ้า key เดิมแต่จำนวนเงินเปลี่ยน ควรตอบ `409 Conflict` ไม่ใช่เงียบ ๆ คืนผลเก่า
- **ตั้ง TTL ให้เหมาะ** payroll ควรเก็บนานกว่าปกติ (เป็นเดือน) เพราะ reconcile กับธนาคารอาจมาทีหลังหลายวัน

อีกชั้นที่ควรมีคู่กัน: **unique constraint ระดับ database** เช่น `UNIQUE(payroll_run_id, employee_id)` ในตารางรายการจ่าย ต่อให้ logic ชั้นบนรั่ว DB ก็ยังกันให้อีกชั้น ซึ่งในงานการเงินถือว่าคุ้มที่จะมีซ้ำซ้อน
