## สรุปสั้นๆ ก่อน

| | Access Token | Refresh Token |
|---|---|---|
| อายุ | สั้นมาก (5–15 นาที) | ยาว (7–30 วัน) |
| ใช้ตอนไหน | แนบไปกับ **ทุก** request | ใช้ตอนขอ access token ใบใหม่เท่านั้น |
| ส่งไปที่ไหนบ้าง | ทุก API endpoint | เฉพาะ endpoint `/refresh` |
| เก็บใน DB ไหม | ไม่ (stateless) | เก็บ (เพื่อให้ยกเลิกได้) |

เทียบง่ายๆ คือ access token เหมือนบัตรผ่านที่ห้อยคอเดินเข้าออกตึกได้ทั้งวัน ส่วน refresh token เหมือนบัตรพนักงานที่เอาไปแลกบัตรผ่านใบใหม่ที่เคาน์เตอร์ตอนบัตรเก่าหมดอายุ

## ทำไมต้องมีสองตัว

ปัญหาหลักคือ JWT มันเป็น **stateless** — server ไม่ได้เก็บ session ไว้ที่ไหน แค่เอา public key มา verify ลายเซ็นว่าถูกต้องไหม ถ้าถูกก็ปล่อยผ่าน ข้อดีคือเร็วมาก ไม่ต้องยิง DB ทุก request แต่ข้อเสียคือ **ยกเลิกไม่ได้** ตราบใดที่ token ยังไม่หมดอายุ มันก็ใช้ได้อยู่ดี ต่อให้ user กด logout หรือโดนแบนไปแล้วก็ตาม

ทีนี้ลองคิดว่ามีแค่ token เดียว:

**แบบที่ 1 — token เดียว อายุสั้น 15 นาที**
ปลอดภัยดี โดนขโมยไปก็ใช้ได้แป๊บเดียว แต่ user ต้องพิมพ์ password ใหม่ทุก 15 นาที ซึ่งไม่มีใครทนได้

**แบบที่ 2 — token เดียว อายุยาว 30 วัน**
UX ดี แต่ถ้า token หลุด (XSS, log ที่ไม่ได้ปิด, proxy ที่โดนดัก) แฮ็กเกอร์เข้า account ได้ยาวๆ 30 วัน แล้วเราก็ทำอะไรไม่ได้เพราะยกเลิกไม่ได้

การแยกสองตัวคือการกินเค้กทั้งสองชิ้น:

- **access token** วิ่งไปทั่วทุก request → โอกาสหลุดสูง เลยให้อายุสั้น ความเสียหายจำกัด
- **refresh token** ถูกส่งนานๆ ครั้ง และส่งไปที่ endpoint เดียว → โอกาสหลุดต่ำ เลยให้อายุยาวได้ แถมเก็บลง DB ได้ด้วยเพราะเรียกไม่บ่อย ไม่กระทบ performance → **ลบออกจาก DB เมื่อไหร่ก็ตัดสิทธิ์ได้ทันที**

สรุปคือเราย้ายภาระ "ยกเลิกได้" ไปไว้ที่ตัวที่ถูกเรียกน้อย แล้วปล่อยให้ตัวที่ถูกเรียกบ่อยเป็น stateless ล้วนๆ

## Flow จริงๆ

```
1. login ด้วย user/password
   → ได้ access (15 นาที) + refresh (7 วัน)

2. ยิง API ปกติ
   → Authorization: Bearer <access>

3. access หมดอายุ → server ตอบ 401
   → client ยิง POST /auth/refresh พร้อม refresh token
   → ได้ access ใบใหม่ (+ refresh ใบใหม่ ถ้าทำ rotation)
   → retry request เดิมอัตโนมัติ

4. refresh หมดอายุ / โดนลบจาก DB
   → เด้งไปหน้า login
```

ขั้นตอนที่ 3 ควรทำใน interceptor (axios interceptor หรือ middleware) เพื่อให้ user ไม่รู้สึกอะไรเลย

## เรื่องที่คนมักพลาด

**เก็บ token ไว้ไหน** — refresh token อย่าเก็บใน `localStorage` เด็ดขาด เพราะโดน XSS ขโมยได้ ให้เก็บใน **httpOnly cookie** ที่ JavaScript อ่านไม่ได้ (ตั้ง `Secure` + `SameSite=Strict` ด้วย) ส่วน access token เก็บใน memory ของแอป (ตัวแปร / state) ก็พอ เพราะอายุสั้นอยู่แล้ว รีเฟรชหน้าแล้วหายก็แค่ไปขอใหม่

**Refresh token rotation** — ทุกครั้งที่ refresh ให้ออก refresh token ใบใหม่แล้วยกเลิกใบเก่า ข้อดีคือถ้าใบเก่าถูกเอามาใช้ซ้ำ แปลว่ามีคนขโมยไปแน่ๆ (เพราะเจ้าของตัวจริงต้องถือใบใหม่แล้ว) ให้ **เพิกถอนทั้ง family ทิ้งหมด** แล้วบังคับ login ใหม่ — อันนี้เรียกว่า reuse detection

**อย่าใส่ข้อมูลอ่อนไหวใน payload** — JWT แค่ **เซ็น** ไม่ได้ **เข้ารหัส** ใครก็ตามที่ถือ token ไปแปะใน jwt.io ก็อ่าน payload ได้หมด ใส่แค่ user id, role, permission พอ อย่าใส่เบอร์โทร เลขบัตรประชาชน หรืออะไรทำนองนั้น

**access token สั้นไม่ได้แปลว่าปลอดภัยเต็มร้อย** — ช่วง 15 นาทีนั้นยังโดนใช้งานได้อยู่ ถ้าระบบคุณเป็นงานที่ sensitive มากๆ (โอนเงิน, เปลี่ยน password) ควรมีการ re-authenticate ซ้ำตรงจุดนั้นแยกอีกชั้น
