ของพวกนี้พังตรงที่คนชอบเริ่มผิดจุด — คือไล่เขียน test ให้ครบทุกไฟล์ตั้งแต่แรก แล้วก็ท้อตายกลางทาง ลำดับที่เวิร์กกว่าคือแบบนี้

## 1. ทำให้ test ตัวแรกรันได้ก่อน (แค่ตัวเดียวพอ)

งานยากที่สุดของ legacy project ไม่ใช่การเขียน test แต่คือการตั้ง test runner ให้มันรันผ่านครั้งแรก — config, path alias, build step, mock env var อะไรพวกนี้

เพราะงั้น test ตัวแรกให้เขียนอะไรก็ได้ที่โง่ที่สุด เช่น เช็คว่าฟังก์ชัน format เบอร์โทรคืนค่าถูก แล้วต่อเข้า CI ให้มันรันทุก PR เลย พอมีรางวิ่งแล้ว ที่เหลือมันง่ายขึ้นเยอะ

## 2. จับ pure logic ก่อน

ไล่หาโค้ดที่ไม่แตะ DB ไม่ยิง HTTP ไม่อ่านเวลาปัจจุบัน — พวกคำนวณราคา, คิดภาษี, validate ฟอร์ม, parse ข้อมูล, แปลง format

ตรงนี้คุ้มสุดเพราะเขียน test ได้โดยไม่ต้อง mock อะไรเลย และมักเป็นจุดที่ bug แพงที่สุดด้วย (คิดเงินผิดนี่เจ็บกว่า UI เพี้ยนเยอะ)

## 3. ใช้ bug เป็นตัวตั้ง

ตั้งกฎว่า **ทุกครั้งที่แก้ bug ต้องเขียน test ที่ fail ก่อนแก้** พอแก้เสร็จ test ผ่าน

ข้อดีคือคุณไม่ต้องเดาว่าควร test ตรงไหน — production บอกคุณมาแล้วว่าตรงไหนพัง และมันพิสูจน์ด้วยว่าแก้ถูกจริง ไม่ใช่แก้มั่ว

## 4. โค้ดที่กำลังจะแก้ ให้ครอบด้วย characterization test ก่อน

ถ้าต้องไปแก้โมดูลเก่าที่ไม่กล้าแตะ ให้เขียน test ที่บันทึก "พฤติกรรมปัจจุบัน" ไว้ก่อน — ไม่ต้องสนว่ามันถูกตามสเปคไหม สนแค่ว่าตอนนี้มันคืนค่าอะไร

พอมีตาข่ายรองแล้วค่อยแก้ ถ้าเผลอทำพังจะรู้ทันที

## 5. ตั้ง ratchet ไว้

กฎง่าย ๆ คือ **โค้ดใหม่ต้องมี test** ส่วนโค้ดเก่าปล่อยไว้ก่อน ค่อย ๆ กินทีละชิ้นตามข้อ 3-4

coverage มันจะไต่ขึ้นเองตามธรรมชาติ ไม่ต้องไปตั้งเป้า 80% แล้วนั่งเขียน test ให้ getter/setter ให้เสียเวลา

---

**สองอย่างที่อยากเตือน**

อย่าเพิ่ง refactor ยกใหญ่เพื่อให้โค้ดมัน testable — มันย้อนแย้งในตัวเอง คุณกำลังจะแก้โค้ดที่ไม่มี test คุ้มกัน ถ้าจำเป็นต้องแยก dependency จริง ๆ ให้ใช้วิธีที่เสี่ยงน้อยสุดก่อน เช่น extract เป็นฟังก์ชันเล็ก ๆ หรือรับ dependency ผ่าน parameter แทนที่จะ new ข้างใน

อีกอย่างคือ ถ้าโค้ดมันพันกันจน mock แล้วเหนื่อยกว่าเขียน logic เอง — **ข้าม unit test ไปเขียน integration test เลยคุ้มกว่า** ยิง API จริง ต่อ test database จริง (หรือ in-memory/testcontainer) เช็ค response กับ state ใน DB กับ legacy code ส่วนใหญ่ integration test ให้ความมั่นใจต่อแรงที่ลงไปสูงกว่า unit test เยอะ

---

ถ้าบอก stack ได้ (Angular? .NET? Node?) จะแนะนำได้ตรงกว่านี้ ว่าควรใช้ตัวไหนและจุดที่มักติดคืออะไร
