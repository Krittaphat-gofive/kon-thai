Idempotency คือการที่เรียก API เดิมซ้ำกี่ครั้ง ผลลัพธ์ที่เกิดกับระบบก็ยังเหมือนเดิมครับ ยิงรอบเดียวกับยิงห้ารอบ เงินต้องออกแค่ก้อนเดียว

## ทำไมเรื่องนี้สำคัญกับ payroll

ปัญหาคลาสสิกคือฝั่ง client ไม่มีทางแยกออกว่า "server ไม่ได้ทำ" กับ "server ทำเสร็จแล้วแต่ response หายระหว่างทาง" สองอันนี้หน้าตาเหมือนกันหมด คือ timeout

พอแยกไม่ออก client ก็ retry และถ้า endpoint จ่ายเงินไม่ idempotent รอบที่สองก็สร้างรายการจ่ายใหม่อีกใบ

จุดที่ทำให้ retry เกิดโดยที่เราไม่ได้สั่งเอง
- network หลุด หรือ load balancer ตัด connection ตอน request ยังค้างอยู่
- pod restart / deploy ระหว่างที่ job กำลังรัน
- message queue ส่วนใหญ่รับประกันแค่ at-least-once ไม่ใช่ exactly-once
- scheduler ที่ตั้ง retry policy ไว้เอง
- HR กดปุ่ม "จ่ายเงินเดือน" สองทีเพราะหน้าจอค้าง

ที่ payroll เจ็บกว่าระบบอื่นเพราะเงินออกจากบัญชีบริษัทไปจริง จะดึงคืนต้องไปขอคืนจากพนักงานทีละคน แล้วยอดที่เพี้ยนไม่ได้มีแค่เงินโอน ภาษีหัก ณ ที่จ่าย ประกันสังคม ยอดสะสมทั้งปี กองทุนสำรองเลี้ยงชีพ พังตามกันไปหมด ตอนปิดงบสิ้นปีจะตามแก้กันยาว

## HTTP method ช่วยได้แค่บางส่วน

| method | idempotent ไหม |
|---|---|
| GET, HEAD | ใช่ โดยนิยาม |
| PUT, DELETE | ใช่ ถ้าเขียน handler ถูก |
| POST | ไม่ ต้องทำเองทั้งหมด |

ตรงนี้คนพลาดกันบ่อย คือคิดว่าใช้ PUT แล้วจะ idempotent อัตโนมัติ จริง ๆ spec บอกแค่ว่า method นี้ควรมีความหมายแบบนั้น ถ้าใน handler เขียน `INSERT` ทุกครั้ง ก็ไม่ idempotent อยู่ดี

## วิธีทำจริง

**1. Idempotency key**

ให้ client ส่ง key มาต่อหนึ่งงาน ผ่าน header

```http
POST /api/payroll/runs
Idempotency-Key: payroll-2026-09-batch-01
```

ฝั่ง server เก็บลงตารางที่มี unique index บน key พร้อม response ที่ตอบไปรอบแรก พอเจอ key ซ้ำก็คืนของเดิมกลับไปเลย ไม่ต้องรันงานใหม่

key ควร gen จากฝั่งที่เริ่มงาน และต้องคงที่ตลอดการ retry ถ้า client gen uuid ใหม่ทุกครั้งที่ retry ก็ไม่มีประโยชน์

**2. Unique constraint ที่ database เป็นด่านสุดท้าย**

```sql
ALTER TABLE payslip
ADD CONSTRAINT uq_payslip_employee_period UNIQUE (employee_id, period_id);
```

ด่านนี้สำคัญ เพราะ logic ใน application layer พลาดได้ แต่ constraint ที่ db ไม่พลาด พนักงานหนึ่งคนในหนึ่งงวด มีสลิปได้ใบเดียว จบ

**3. จัดการช่วง in-flight**

กรณีที่คนลืมคิดกันมากที่สุด คือ request แรกยังทำงานค้างอยู่ แล้วอันที่สองเข้ามาด้วย key เดิม ถ้าปล่อยผ่านก็รันพร้อมกันสองงาน

ทางแก้คือ insert key ลงตารางพร้อม status `processing` ก่อนเริ่มงานจริง ถ้า insert ชนก็เช็ก status แล้วตอบ 409 กลับไป ให้ client รอแล้วค่อยถามใหม่

## ข้อควรระวัง

- key เดิม แต่ body ต่าง ให้ตอบ 422 ไปเลย อย่าคืน response เก่า เพราะอาจเป็นบั๊กฝั่ง client ที่ใช้ key ซ้ำผิดงาน เก็บ hash ของ body ไว้เทียบด้วย
- ตั้ง TTL ให้ key เช่น 24-48 ชั่วโมง ไม่งั้นตารางบวมเรื่อย ๆ แต่อย่าสั้นกว่าเวลาที่ retry ยังเกิดได้
- งาน payroll ที่รันเป็นพัน record ไม่ควรทำแบบ synchronous ให้คืน job id แล้วให้ client poll status จะคุมเรื่อง retry ง่ายกว่ามาก

ถ้าบอกมาว่าตอนนี้ฝั่งจ่ายเงินออกแบบไว้ยังไง เดี๋ยวช่วยดูให้ว่าควรวาง key ตรงจุดไหนครับ
