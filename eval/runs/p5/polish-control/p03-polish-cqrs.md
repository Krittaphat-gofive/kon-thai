โฟลเดอร์ที่เปิดอยู่ว่างเปล่า ผมเลยยังไม่เห็นโค้ดระบบ HR ของคุณ — ขออธิบาย CQRS ให้ฟังก่อน แล้วค่อยให้เกณฑ์ว่าเคสไหนคุ้มเคสไหนไม่คุ้ม ปิดท้ายด้วยข้อมูลที่ผมต้องรู้เพิ่ม ถึงจะฟันธงให้ได้จริงๆ

## CQRS คืออะไร

**Command Query Responsibility Segregation** = แยก "ฝั่งเขียน" กับ "ฝั่งอ่าน" ออกจากกันเป็นคนละโมเดล

CRUD แบบที่ทำกันปกติใช้โมเดลเดียวจบทุกงาน — `Employee` ตัวเดียวกันทั้งตอนบันทึก ตอนดึงไปโชว์ ตอนทำรายงาน ปัญหาคือสองฝั่งต้องการคนละอย่างกัน ฝั่งเขียนอยากได้โมเดลที่คุม business rule อยู่หมัด (เช่น "วันลาคงเหลือห้ามติดลบ") ส่วนฝั่งอ่านขอแค่ข้อมูลแบนๆ ที่ตรงกับหน้าจอ ไม่ต้อง join 8 ตาราง

CQRS แยกเป็น:
- **Command side** — รับคำสั่ง (`ApproveLeaveRequest`, `AdjustSalary`) → validate → เปลี่ยน state ผ่าน domain model ปกติไม่คืนข้อมูลอะไรกลับมานอกจากสำเร็จ/ไม่สำเร็จ
- **Query side** — อ่านจาก read model ที่ปั้นมาเพื่อหน้าจอนั้นโดยเฉพาะ ข้าม domain model ไปเลย จะยิง SQL ตรงเข้า view หรือตาราง denormalized ก็ได้

## มันมี 3 ระดับ แต่คนมักเหมารวมเป็นอันเดียว

| ระดับ | ทำอะไร | ต้นทุน |
|---|---|---|
| 1. แยกแค่ในโค้ด | แยก `CommandHandler` กับ `QueryHandler` แต่ใช้ DB เดียวกัน (แนว MediatR) | ต่ำมาก ได้โค้ดที่อ่านง่ายขึ้นมาฟรีๆ |
| 2. แยก read model ใน DB เดียวกัน | ทำ materialized view หรือตาราง denormalized ไว้รองรับ query หนักๆ | ปานกลาง ยังอยู่ใน transaction เดียวกันได้อยู่ |
| 3. แยก datastore คนละที่ | เขียนลง Postgres อ่านจาก Elasticsearch/Redis แล้ว sync ด้วย event | สูง ได้ **eventual consistency** มาเป็นของแถม |

ตัวที่เจ็บคือระดับ 3 — eventual consistency แปลว่าผู้ใช้กดบันทึกแล้ว refresh ยังอาจไม่เห็นข้อมูลใหม่ ใน HR เรื่องนี้พังง่ายมาก เพราะมี flow อนุมัติเต็มไปหมด ("ก็อนุมัติไปแล้วไง ทำไมยังขึ้นว่ารอดำเนินการ") ต้องออกแบบ UX มารองรับด้วย ไม่ใช่ปัญหาฝั่ง backend อย่างเดียว

อีกเรื่อง: **CQRS ≠ Event Sourcing** สองตัวนี้มาด้วยกันบ่อยจนคนเข้าใจผิดว่าต้องใช้คู่กัน จริงๆ แยกกันได้สบาย

## ระบบ HR เหมาะไหม

ลองดูลักษณะที่ระบบ HR มักเป็น แล้วตีความได้ว่า:

**เข้าทาง CQRS**
- read-heavy ชัดเจน — org chart ค้นหาพนักงาน dashboard รายงาน พวกนี้อ่านมากกว่าเขียนหลายสิบเท่า
- รายงานกับ payroll ต้อง join หนักและ aggregate ข้ามงวด — แยก read model ออกมาแล้วดีขึ้นเห็นๆ
- ต้องมี audit trail แน่นหนา (ประวัติปรับเงินเดือน เลื่อนตำแหน่ง โอนย้าย) — ตรงนี้ทำ event sourcing เฉพาะ aggregate นั้นน่าสนใจ เพราะ HR ต้องตอบให้ได้ว่า "ณ วันที่ 1 ม.ค. ปีที่แล้ว คนนี้อยู่แผนกไหน เงินเดือนเท่าไร"

**ไม่เข้าทาง**
- transaction volume ต่ำ พนักงานหลักพันถึงหลักหมื่น ไม่ใช่ระบบ e-commerce ที่ยิงวินาทีละพัน request — เหตุผลเรื่อง scale ที่คนชอบยกมาอ้างกันแทบไม่เกิดกับ HR
- หลายส่วนเป็น CRUD ตรงๆ จริงๆ — แก้ที่อยู่ แก้เบอร์โทร ตั้งค่า master data ประเภทการลา ลาก CQRS มาใส่ตรงนี้คือเพิ่มไฟล์อีก 4 ไฟล์ให้กับงานที่ `UPDATE` บรรทัดเดียวก็จบ
- บาง flow ต้อง read-after-write ทันที — ยอดวันลาคงเหลือ สถานะอนุมัติ ผลคำนวณ payroll ถ้าปล่อยให้ eventual consistency เข้ามาตรงนี้คือหายนะ

## คำแนะนำ

**อย่าใช้ทั้งระบบ** — ให้เลือกใช้เป็นราย bounded context จุดที่โปรเจกต์ส่วนใหญ่พลาดคือไปตัดสินใจระดับสถาปัตยกรรมเหมารวมทั้งก้อน แทนที่จะหยิบมาใช้เฉพาะตรงที่มีปัญหาจริง

ถ้าเป็นผม จะทำกับระบบ HR แบบนี้:
1. **ระดับ 1 ใช้ทั้งระบบ** — แยก command/query handler เป็นการจัดระเบียบโค้ดที่ดี ต้นทุนแทบเป็นศูนย์ และไม่มีเรื่อง eventual consistency มาเกี่ยวเลย
2. **ระดับ 2 เฉพาะรายงาน/dashboard/search** — แยก read model เฉพาะตรงที่ query ช้าจริง วัดก่อนแล้วค่อยทำ
3. **ระดับ 3 พักไว้ก่อน** — รอจนกว่าจะมีเหตุผลที่วัดออกมาเป็นตัวเลขได้ เช่น รายงานไป lock ตาราง production จนคนยื่นลาไม่ได้
4. **Event sourcing เฉพาะ aggregate ที่ต้องการประวัติ** — employment history กับ compensation ส่วนที่เหลือไม่ต้อง

## ขอข้อมูลเพิ่มหน่อย เดี๋ยวฟันธงให้ชัดกว่านี้

ที่ว่ามาทั้งหมดเป็นกรอบกว้างๆ ถ้าจะชี้ให้ตรงเคสของคุณ ผมต้องรู้ว่า:

1. **ตอนนี้เจอปัญหาอะไรอยู่** — query ช้า? รายงานทำ DB ล่ม? โค้ดรก business logic กระจัดกระจาย? หรือกำลังจะเขียนใหม่ทั้งหมด? แต่ละข้อพาไปคนละทางเลย
2. **ใช้ stack อะไร** — .NET / Node / Java แล้วใช้ ORM ตัวไหน
3. **ขนาดระบบ** — พนักงานกี่คน กี่ tenant ช่วง peak (ต้นเดือน / ปิด payroll) มี concurrent user ประมาณเท่าไร
4. **ทีมกี่คน เคยทำ CQRS มาก่อนไหม** — ข้อนี้สำคัญไม่แพ้เรื่องเทคนิค เพราะ CQRS ในมือทีมที่ไม่คุ้น สุดท้ายมักกลายเป็น CRUD ที่ไฟล์เยอะขึ้นเฉยๆ

ถ้าบอก path ของโค้ดระบบ HR มาได้ ผมจะเข้าไปอ่านแล้วชี้ให้เลยว่าควรแยก read model ตรงไหนก่อน
