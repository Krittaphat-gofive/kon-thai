เริ่มจากความคิดเดียวก่อนค่ะ unit test คือโค้ดที่เรียกฟังก์ชันของเราด้วยค่าที่รู้คำตอบอยู่แล้ว แล้วเช็กว่าผลที่ได้ตรงกับที่คาดไว้ไหม ไม่มีอะไรมากกว่านั้น

ตัวอย่างข้างล่างใช้ Python กับ pytest เพราะในโปรเจกต์นี้มีสคริปต์ Python อยู่แล้ว (`run_eval.py`, `thai_lint.py`) แต่หลักคิดเหมือนกันหมดทุกภาษา

## โครง 3 บรรทัดที่ใช้ได้กับทุก test

เตรียมข้อมูล → เรียกฟังก์ชัน → เช็กผล

สมมติมีฟังก์ชันนี้

```python
# pricing.py
def apply_discount(price, percent):
    if percent < 0 or percent > 100:
        raise ValueError("percent must be 0-100")
    return price * (100 - percent) / 100
```

test จะหน้าตาแบบนี้

```python
# test_pricing.py
import pytest
from pricing import apply_discount


def test_apply_discount_returns_discounted_price():
    price = 100                           # เตรียม
    result = apply_discount(price, 10)    # เรียก
    assert result == 90                   # เช็ก
```

`assert` คือคำสั่งเดียวที่ต้องรู้ ถ้าเงื่อนไขหลัง assert เป็นจริง test ผ่าน ถ้าเป็นเท็จ test พังแล้ว pytest จะพิมพ์ให้ดูว่าได้ค่าอะไรมาแทน

## รันยังไง

ตั้งชื่อไฟล์ขึ้นต้นด้วย `test_` และชื่อฟังก์ชันขึ้นต้นด้วย `test_` ด้วย แล้วสั่ง

```powershell
python -m pytest -q
```

pytest จะไล่หาไฟล์กับฟังก์ชันตามชื่อนี้เอง ไม่ต้องไป register ที่ไหน

## เลือกจะ test เคสไหนดี

จับ 3 กลุ่มนี้ต่อหนึ่งฟังก์ชัน ก็ครอบคลุมพอสำหรับงานทั่วไปแล้ว

1. ทางปกติ: ค่าที่ user ใส่กันจริง เช่น ลด 10%
2. ค่าขอบ: 0, ค่าสูงสุด, string ว่าง, list ว่าง, `None` พวกนี้พังบ่อยที่สุด
3. ทางที่ต้องพัง: ใส่ค่าผิดแล้วต้องได้ error ตามที่ออกแบบไว้

กลุ่มที่ 3 เขียนแบบนี้

```python
def test_apply_discount_rejects_percent_over_100():
    with pytest.raises(ValueError):
        apply_discount(100, 101)
```

แปลว่า "ในบล็อกนี้ต้องเกิด ValueError" ถ้าไม่เกิด test จะพัง

## พอเคสเยอะ ไม่ต้องก๊อปฟังก์ชันซ้ำ

ใช้ `parametrize` ยัดหลายเคสลง test เดียว pytest จะนับเป็นคนละ test ให้เอง

```python
@pytest.mark.parametrize("price, percent, expected", [
    (100, 0, 100),
    (100, 10, 90),
    (100, 100, 0),
])
def test_apply_discount(price, percent, expected):
    assert apply_discount(price, percent) == expected
```

## ข้อผิดพลาดที่คนเพิ่งเริ่มเจอบ่อย

- **ยัดหลายเรื่องใน test เดียว** พอพังจะไม่รู้ว่าพังเพราะอะไร หนึ่ง test เช็กหนึ่งพฤติกรรม
- **ชื่อ test ว่า `test_1`, `test_2`** ตั้งชื่อให้อ่านแล้วรู้เลยว่าเช็กอะไร เวลา CI พังจะอ่านชื่อแล้วเดาต้นเหตุได้ทันที
- **test ที่ไม่มีวันพัง** เช่น `assert result is not None` ลองแก้โค้ดให้ผิดดู ถ้า test ยังผ่านอยู่ แปลว่า test นั้นไม่ได้ช่วยอะไร
- **เรียก DB หรือ API จริงใน unit test** แบบนั้นช้าและพังตามเน็ต วิธีง่ายสุดคือแยกส่วนที่คิดเลขหรือตัดสินใจออกมาเป็นฟังก์ชันที่รับค่าเข้า คืนค่าออก ไม่ยุ่ง I/O แล้ว test เฉพาะส่วนนั้น ส่วนที่ยิง API ค่อยไปทดสอบอีกแบบ

## เริ่มกับโค้ดที่มีอยู่แล้วยังไง

อย่าเพิ่งไล่เขียนให้ครบทุกไฟล์ เลือกฟังก์ชันที่รับค่าเข้าแล้วคืนค่าออกตรง ๆ สัก 1 ตัว เขียน test ให้มัน 3 เคสตามข้างบน รันให้เขียวก่อน แล้วค่อยขยายไปตัวถัดไป อีกจังหวะที่คุ้มมากคือตอนเจอบั๊ก เขียน test ที่จำลองบั๊กนั้นให้พังก่อน แล้วค่อยแก้โค้ดจน test ผ่าน จะได้มั่นใจว่าแก้ตรงจุดจริงและบั๊กเดิมจะไม่กลับมาเงียบ ๆ

โปรเจกต์ที่อยากเริ่มเขียน test ใช้ภาษาอะไรอยู่คะ ถ้าเป็น C# หรือ TypeScript เดี๋ยวแปลงตัวอย่างชุดนี้ให้ตรงกับเฟรมเวิร์กที่ใช้
