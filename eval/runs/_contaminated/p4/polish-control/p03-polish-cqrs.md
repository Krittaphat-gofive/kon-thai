เกลาแล้วครับ เนื้อหา โครงสร้าง และศัพท์เทคนิคคงเดิมทั้งหมด ปรับเฉพาะสำนวนให้เป็นไทยที่คนเขียนจริง

---

โฟลเดอร์งานยังว่างอยู่ เลยยังไม่เห็นโค้ดระบบ HR ครับ ขออธิบาย CQRS ก่อน แล้วค่อยให้เกณฑ์ว่าเคสไหนคุ้ม เคสไหนไม่คุ้ม พร้อมคำถามที่ต้องรู้ถึงจะฟันธงได้จริง

## CQRS คืออะไร

**Command Query Responsibility Segregation** คือการแยกฝั่งเขียนกับฝั่งอ่านออกเป็นคนละโมเดล

CRUD ปกติใช้โมเดลเดียวทำทุกอย่าง `Employee` ตัวเดียวทั้งตอนบันทึก ตอนดึงไปโชว์ ตอนทำรายงาน ปัญหาคือสองฝั่งต้องการคนละแบบ ฝั่งเขียนอยากได้โมเดลที่คุม business rule ได้แน่น (เช่น "วันลาคงเหลือห้ามติดลบ") ส่วนฝั่งอ่านขอแค่ข้อมูลแบน ๆ ที่ตรงกับหน้าจอ ไม่ต้อง join 8 ตาราง

CQRS แยกเป็น

- **Command side**: รับคำสั่ง (`ApproveLeaveRequest`, `AdjustSalary`) แล้ว validate จากนั้นเปลี่ยน state ผ่าน domain model ปกติไม่คืนข้อมูลกลับ บอกแค่สำเร็จหรือไม่สำเร็จ
- **Query side**: อ่านจาก read model ที่ปั้นมาเพื่อหน้าจอนั้นโดยเฉพาะ ข้าม domain model ไปเลย จะยิง SQL ตรงเข้า view หรือตาราง denormalized ก็ได้

## มี 3 ระดับ ที่คนมักเหมารวมเป็นอันเดียวกัน

| ระดับ | ทำอะไร | ต้นทุน |
|---|---|---|
| 1. แยกแค่ในโค้ด | แยก `CommandHandler` / `QueryHandler` ใช้ DB เดียวกัน (สไตล์ MediatR) | ต่ำมาก ได้โค้ดที่อ่านง่ายขึ้นมาฟรี ๆ |
| 2. แยก read model ใน DB เดียวกัน | ทำ materialized view หรือตาราง denormalized ไว้รองรับ query หนัก ๆ | ปานกลาง ยังอยู่ใน transaction เดียวกันได้ |
| 3. แยก datastore คนละที่ | เขียนลง Postgres อ่านจาก Elasticsearch/Redis แล้ว sync ด้วย event | สูง แถม **eventual consistency** มาด้วย |

ที่เจ็บคือระดับ 3 เพราะ eventual consistency แปลว่า user กดบันทึกแล้ว refresh อาจยังไม่เห็นข้อมูลใหม่ ระบบ HR เจอเรื่องนี้แล้วพังง่าย เพราะมี flow อนุมัติเยอะ ("กดอนุมัติไปแล้ว ทำไมยังขึ้นว่ารอดำเนินการอยู่") ต้องออกแบบ UX มารองรับด้วย ไม่ใช่เรื่องของ backend อย่างเดียว

อีกอย่าง **CQRS ≠ Event Sourcing** สองตัวนี้มักมาคู่กันจนหลายคนเข้าใจว่าต้องใช้ด้วยกัน จริง ๆ แยกกันได้

## ระบบ HR เหมาะไหม

ระบบ HR ส่วนใหญ่มีลักษณะแบบนี้ ซึ่งตีความได้ว่า

**เข้าทาง CQRS**

- read-heavy ชัดเจน ทั้ง org chart ค้นหาพนักงาน dashboard รายงาน ปริมาณอ่านมากกว่าเขียนหลายสิบเท่า
- รายงานกับ payroll ต้อง join หนักและ aggregate ข้าม period พวกนี้แยก read model ออกมาแล้วดีขึ้นเห็น ๆ
- ต้องการ audit trail แน่นหนา (ประวัติปรับเงินเดือน เลื่อนตำแหน่ง โอนย้าย) ตรงนี้ใช้ event sourcing เฉพาะ aggregate นั้นน่าสนใจ เพราะ HR ต้องตอบให้ได้ว่า "วันที่ 1 ม.ค. ปีที่แล้ว คนนี้อยู่แผนกไหน เงินเดือนเท่าไร"

**ไม่เข้าทาง**

- transaction volume ต่ำ พนักงานหลักพันถึงหลักหมื่น ไม่ใช่ระบบ e-commerce ที่ยิงวินาทีละพัน request เหตุผลเรื่อง scale ที่คนมักยกมาอ้างแทบไม่เกิดกับ HR
- หลายส่วนเป็น CRUD ตรง ๆ จริง ๆ ทั้งแก้ที่อยู่ แก้เบอร์โทร ตั้งค่า master data ประเภทการลา ทำ CQRS ตรงนี้คือเพิ่มไฟล์ 4 ไฟล์ให้งานที่ `UPDATE` บรรทัดเดียวก็จบ
- บาง flow ต้องการ read-after-write ทันที ทั้งยอดวันลาคงเหลือ สถานะอนุมัติ ผลคำนวณ payroll ถ้า eventual consistency โผล่มาตรงนี้คือหายนะ

## คำแนะนำ

**อย่าใช้ทั้งระบบ** ให้เลือกใช้เป็นราย bounded context จุดที่โปรเจกต์ส่วนใหญ่พลาดคือไปตัดสินใจระดับสถาปัตยกรรมทั้งก้อน แทนที่จะเลือกทำเฉพาะตรงที่มีปัญหาจริง

ถ้าเป็นผม จะทำกับระบบ HR แบบนี้

1. **ระดับ 1 ทั้งระบบ** แยก command/query handler ถือเป็นการจัดระเบียบโค้ดที่ดี ต้นทุนเกือบเป็นศูนย์ และไม่มีเรื่อง eventual consistency มาเกี่ยว
2. **ระดับ 2 เฉพาะรายงาน/dashboard/search** ทำ read model แยกตรงที่ query ช้าจริง วัดก่อนแล้วค่อยทำ
3. **ระดับ 3 เก็บไว้ก่อน** จนกว่าจะมีเหตุผลที่วัดได้ เช่น รายงานไป lock ตาราง production จนคนลางานไม่ได้
4. **Event sourcing เฉพาะ aggregate ที่ต้องเก็บประวัติ** อย่าง employment history กับ compensation ส่วนอื่นไม่ต้อง

## ขอข้อมูลเพิ่มเพื่อฟันธงให้ชัด

ที่ตอบไปเป็นกรอบกว้าง ๆ ถ้าจะชี้ให้เฉพาะเจาะจงต้องรู้ว่า

1. **ตอนนี้ติดปัญหาอะไร** query ช้า? รายงานทำ DB ตาย? โค้ดรก business logic กระจัดกระจาย? หรือกำลังจะเขียนใหม่ทั้งหมด? แต่ละคำตอบพาไปคนละทางเลย
2. **ใช้ stack อะไร** .NET / Node / Java และใช้ ORM ตัวไหน
3. **ขนาดเท่าไร** พนักงานกี่คน กี่ tenant ช่วง peak (ต้นเดือน/ปิด payroll) มี concurrent user ประมาณเท่าไร
4. **ทีมกี่คน** และเคยทำ CQRS มาก่อนไหม ข้อนี้สำคัญพอ ๆ กับเรื่องเทคนิค เพราะ CQRS ในทีมที่ไม่คุ้นมักจบลงที่ CRUD ที่มีไฟล์เยอะขึ้นเฉย ๆ

ถ้าชี้ path โค้ดระบบ HR มาให้ได้ ผมอ่านแล้วบอกได้เลยครับว่าควรแยก read model ตรงไหนก่อน
