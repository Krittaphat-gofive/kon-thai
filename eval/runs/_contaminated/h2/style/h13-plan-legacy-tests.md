เริ่มจากโค้ดที่กำลังจะแก้ครับ ไม่ใช่ไล่เขียนจากไฟล์แรกของโปรเจกต์

โปรเจกต์เก่าที่ไม่มี test เลย ถ้าตั้งเป้าว่า "จะเขียนให้ครบ" คือจบไม่ลง เขียนไปสักพักก็เลิก กลยุทธ์ที่ได้ผลกว่าคือให้ test โตตามงานที่ทำอยู่แล้ว

## 1. ทำให้รัน test ได้ด้วยคำสั่งเดียวก่อน

ก่อนจะเขียน test ตัวแรก ตั้ง test project + runner ให้เรียบร้อย แล้วเขียน test ปลอม ๆ หนึ่งตัวที่ assert `1 + 1 == 2` แค่ให้เห็นว่าสีเขียวขึ้นจริง จากนั้นต่อเข้า CI ให้รันทุก PR

ขั้นนี้ดูไร้สาระแต่สำคัญ ถ้ารัน test แล้วต้องตั้งค่า 5 อย่างก่อน หรือรันแล้วพังบ้างผ่านบ้าง สุดท้ายไม่มีใครในทีมเขียนเพิ่ม

## 2. เลือกเป้าหมายแรกจาก "พังแล้วเจ็บ" คูณ "แก้บ่อย"

เรียงลำดับจาก
- logic ที่เกี่ยวกับเงิน การคิดราคา ภาษี ส่วนลด สิทธิ์การเข้าถึง พวกนี้พังแล้วเสียหายจริง
- ไฟล์ที่ git log บอกว่าแก้บ่อยที่สุดในปีที่ผ่านมา โค้ดที่แก้บ่อยคือโค้ดที่พังบ่อย
- จุดที่เพิ่งมีบั๊กเข้ามา

ในกลุ่มนี้ให้หยิบส่วนที่ test ง่ายที่สุดขึ้นมาก่อน คือ pure logic ที่รับ input ออก output ไม่แตะ DB ไม่ยิง HTTP ได้แต้มเร็วและทีมเห็นประโยชน์ทันที

## 3. เวลาเจอบั๊ก ให้เขียน test ก่อนแก้

นี่เป็นนิสัยที่คุ้มที่สุดข้อเดียว พอมี bug report เข้ามา เขียน test ที่ reproduce บั๊กนั้นให้แดงก่อน แล้วค่อยแก้โค้ดจนเขียว

ได้สองอย่างพร้อมกัน: ยืนยันว่าแก้ถูกจุดจริง และบั๊กเดิมจะไม่กลับมาอีก test suite จะค่อย ๆ โตตามจุดที่โปรเจกต์เคยพังจริง ซึ่งตรงเป้ากว่าการนั่งเดาว่าควร test อะไร

## 4. โค้ดที่ test ไม่ได้เพราะ dependency ผูกแน่น

ปัญหาคลาสสิกของ legacy คือ method เดียวทั้งอ่าน DB ทั้งส่งอีเมลทั้งคำนวณ แยกไม่ออก ทางออกมีสองแบบ

ถ้าแกะได้ ให้ extract logic การคำนวณออกมาเป็น method หรือ class แยกที่รับค่าเข้าไปตรง ๆ แล้ว test เฉพาะส่วนนั้น ส่วนที่คุยกับ DB ปล่อยไว้ก่อน

ถ้าแกะยากเกิน ให้เขียน characterization test ครอบระดับบนแทน คือยิงเข้า endpoint หรือเรียก service ตัวนอกสุด แล้วบันทึกผลลัพธ์ปัจจุบันไว้เป็น expected ไม่ต้องสนว่าพฤติกรรมนั้นถูกหรือผิด จุดประสงค์คือล็อกไว้ว่า "วันนี้ระบบทำแบบนี้" เพื่อให้ refactor ต่อได้อย่างปลอดภัย พอ refactor เสร็จค่อยเขียน unit test จริงลงไป

## 5. สิ่งที่ไม่ต้องทำ

- อย่าตั้ง KPI เป็น coverage รวมทั้งโปรเจกต์ เลขจะสวยขึ้นด้วย test ที่ไม่ assert อะไรเลย ถ้าจะวัด ให้วัด coverage เฉพาะโค้ดที่เปลี่ยนใน PR นั้น
- อย่าเขียน test ให้ getter/setter, DTO mapper ตรง ๆ, หรือ wrapper บาง ๆ ที่แค่เรียกต่อไปอีกชั้น ดูแลเปลืองแรงแต่ไม่กันบั๊ก
- อย่า mock ทุกอย่างจนเหลือแต่การเช็กว่า "เรียก method นี้กี่ครั้ง" test แบบนั้นพังทุกครั้งที่ refactor ทั้งที่พฤติกรรมไม่เปลี่ยน

ถ้าบอก stack ที่ใช้มาได้ (เช่น .NET, Node, Java) เดี๋ยวผมแนะนำ framework กับวิธีวาง test project ให้เจาะจงกว่านี้ครับ
