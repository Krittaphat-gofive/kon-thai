สรุปสั้น ๆ คือมีสองตัวเพราะต้องแลกกันระหว่างความเร็วกับความปลอดภัย ตัวเดียวทำทั้งสองอย่างพร้อมกันไม่ได้ครับ

## ปัญหาที่ทำให้ต้องแยกเป็นสองตัว

จุดขายของ JWT คือ server ตรวจ token ได้จาก signature กับ `exp` ที่อยู่ในตัว token เอง ไม่ต้องยิง query ไปถาม DB ทุก request ข้อเสียที่ตามมาคือ พอออก token ไปแล้วก็เรียกคืนไม่ได้ ต่อให้ผู้ใช้กด logout หรือ admin แบนบัญชีไปแล้ว token ใบนั้นก็ยังผ่านการตรวจอยู่ดีจนกว่าจะหมดอายุ

ทีนี้ลองคิดว่าใช้ token ใบเดียว

- ตั้งอายุ 15 นาที: ปลอดภัย token หลุดไปก็ใช้ได้ไม่นาน แต่ผู้ใช้โดนเด้งไปหน้า login ทุก 15 นาที
- ตั้งอายุ 30 วัน: ผู้ใช้สบาย แต่ถ้า token หลุด คนที่ได้ไปใช้ได้ยาว ๆ 30 วัน ทำอะไรไม่ได้เลย

refresh token เกิดมาเพื่อเอาข้อดีทั้งสองฝั่ง ให้ access token อายุสั้นไว้ใช้งานจริง แล้วมี refresh token อายุยาวคอยต่ออายุให้เบื้องหลัง ผู้ใช้ไม่รู้สึกอะไร

## ความต่างของสองตัว

| | access token | refresh token |
|---|---|---|
| อายุ | 5 - 15 นาที | 7 - 30 วัน |
| แนบไปกับ | ทุก request ที่เรียก API | เฉพาะตอนเรียก `/auth/refresh` |
| server ตรวจยังไง | เช็ก signature กับ `exp` จบ | ต้องเทียบกับที่เก็บไว้ใน DB |
| เก็บที่ไหน (web) | ตัวแปรใน memory | httpOnly + Secure cookie |
| ยกเลิกกลางคันได้ไหม | ไม่ได้ ต้องรอหมดอายุ | ได้ ลบแถวใน DB ทิ้ง |
| หลุดแล้วเสียหายแค่ไหน | จำกัดที่อายุที่เหลือ | หนัก ต่ออายุตัวเองได้เรื่อย ๆ |

ประเด็นสำคัญอยู่ที่สองแถวล่าง refresh token ยอมแลกความเร็วกลับไป คือ server ต้องแตะ DB ทุกครั้งที่ refresh แต่แลกมากับการที่เพิกถอนได้จริง ส่วน access token ยังเร็วเหมือนเดิมเพราะ request ส่วนใหญ่ของระบบใช้ตัวนี้

## flow ที่เกิดขึ้นจริง

1. login สำเร็จ server ออกให้ทั้งคู่
2. client เรียก API แนบ access token มาใน `Authorization: Bearer ...`
3. ครบ 15 นาที access token หมดอายุ API ตอบ 401 กลับไป
4. client ยิง `/auth/refresh` พร้อม refresh token
5. server เช็กใน DB ว่า refresh token ใบนี้ยังใช้ได้อยู่ไหม ถ้าใช่ก็ออก access token ใบใหม่ให้
6. client ยิง request เดิมซ้ำด้วย token ใหม่ ผู้ใช้ไม่เห็นอะไรเลย

## refresh token rotation

ถ้าทำได้แนะนำให้ทำด้วย คือทุกครั้งที่ refresh ให้ออก refresh token ใบใหม่แล้วทำใบเก่าให้ใช้ไม่ได้

ประโยชน์คือตรวจจับการขโมยได้ สมมติคนร้ายก๊อป refresh token ไปแล้วเอาไปใช้ พอเจ้าของตัวจริง refresh ด้วยใบเก่า server จะเห็นว่ามีคนเอาใบที่ใช้ไปแล้วมาใช้ซ้ำ แปลว่ามีคนก๊อปไป ก็สั่ง logout ทุก session ของบัญชีนั้นทิ้งไปเลย

## จุดที่มักพลาดกัน

- **เก็บ refresh token ใน localStorage** อย่าทำ โดน XSS ทีเดียวหลุดหมด ให้ใช้ httpOnly cookie ที่ JavaScript อ่านไม่ได้ ส่วน access token เก็บใน memory พอ reload หน้าแล้วหายก็ค่อย refresh เอาใหม่
- **race condition ตอน refresh** ถ้าหน้าเว็บยิง API พร้อมกัน 5 เส้นแล้วเด้ง 401 พร้อมกัน จะมี 5 request วิ่งไป `/auth/refresh` ซ้อนกัน ถ้าทำ rotation ด้วยยิ่งพัง เพราะใบที่ 2 - 5 กลายเป็นใบเก่าไปแล้ว ทางแก้คือใน interceptor ให้ล็อกไว้ว่า refresh ได้ทีละครั้ง request ที่เหลือรอผลอันแรก
- **logout แล้วลบแค่ฝั่ง client** ต้องลบ refresh token ใน DB ด้วย ไม่งั้นใครที่ก๊อปไปแล้วยังใช้ต่อได้
- **ใส่ข้อมูล sensitive ลงใน payload** JWT แค่ encode base64 ไม่ได้เข้ารหัส ใครก็เปิดอ่านได้

อีกเรื่องที่อยากฝากไว้ ถ้าระบบเป็น web app ตัวเดียวคุยกับ backend ตัวเดียว session cookie ธรรมดาอาจจะตอบโจทย์กว่าและจัดการง่ายกว่าเยอะ JWT กับ refresh token จะคุ้มตอนที่มีหลาย service ต้องตรวจ token เอง หรือมี mobile app มาเรียกด้วย

ถ้ากำลังจะทำจริง บอกมาได้ว่าใช้ stack อะไร เดี๋ยวผมเขียนตัวอย่าง interceptor กับฝั่ง API ให้ดูครับ
