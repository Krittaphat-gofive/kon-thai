เริ่มจากทำให้ test รันได้ก่อน แล้วค่อยเลือกจุดที่คุ้มที่สุดครับ ไม่ใช่ไล่เขียนให้ครบทุกไฟล์

## ลำดับที่แนะนำ

**1. ตั้ง test infrastructure ให้ผ่าน CI ตั้งแต่วันแรก**

ลง test framework แล้วเขียน test โง่ ๆ หนึ่งตัวที่ assert `1 + 1 === 2` ก็ได้ จุดประสงค์คือให้ pipeline มีขั้นตอน `run tests` จริง ๆ ถ้ายังไม่มีตรงนี้ test ที่เขียนทีหลังจะค่อย ๆ พังแล้วไม่มีใครรู้

**2. เริ่มจากโค้ดที่เป็น pure logic**

หาฟังก์ชันที่รับค่าเข้า คืนค่าออก ไม่แตะ database ไม่ยิง API เช่น

- การคำนวณราคา ภาษี ส่วนลด
- validation rule
- การแปลงรูปแบบข้อมูล date, currency, การตัดคำ
- business rule ที่เขียนเป็น if ซ้อนกันหลายชั้น

กลุ่มนี้เขียน test ได้โดยไม่ต้อง mock อะไรเลย ได้ความมั่นใจเร็ว และทำให้ทีมเห็นว่าเขียน test ไม่ได้ยากอย่างที่กลัว

**3. ใช้ git ช่วยเลือกว่าไฟล์ไหนก่อน**

ไฟล์ที่แก้บ่อย คือไฟล์ที่พังบ่อย ลองรันดู

```bash
git log --since="1 year ago" --name-only --pretty=format: | sort | uniq -c | sort -rn | head -30
```

เอารายชื่อที่ได้มาตัดเฉพาะไฟล์ที่มี logic จริง ๆ นั่นคือลิสต์งานของเรา ไฟล์ที่แก้บ่อย + ซับซ้อน คือจุดที่ test ให้ผลตอบแทนสูงสุด

**4. ตั้งกฎสองข้อกับทีม**

- โค้ดใหม่ต้องมี test
- ทุกครั้งที่แก้ bug ให้เขียน test ที่ reproduce bug นั้นก่อน แล้วค่อยแก้ให้ test ผ่าน

สองข้อนี้ทำให้ coverage ค่อย ๆ โตเองตามงานที่ทำอยู่แล้ว โดยไม่ต้องของบ sprint พิเศษมาเขียน test

## ถ้าโค้ดพัน dependency จนเขียน unit test ไม่ได้

เคสนี้เจอบ่อยในโปรเจกต์เก่า เช่น method เดียวเรียก database เรียก service อื่น แล้วส่งอีเมลด้วย อย่าเพิ่งรีบ refactor เพราะยังไม่มี test คุมอยู่ ถ้าแก้แล้วพังจะไม่รู้เลย

ให้ขยับขึ้นไปทดสอบระดับที่สูงกว่าแทน ยิง API endpoint หรือเรียก service ชั้นบนสุด แล้วเช็กผลลัพธ์ที่ออกมา เรียกว่า characterization test คือ test ที่ล็อกพฤติกรรมปัจจุบันไว้ ไม่ได้สนว่าถูกหรือผิด แค่บันทึกว่าตอนนี้ระบบทำอะไรอยู่ พอมีตาข่ายรองแล้ว ค่อยแยก logic ออกมาเป็นฟังก์ชันเล็ก ๆ แล้วเขียน unit test ลงไป

## สิ่งที่ควรเลี่ยง

- **ตั้งเป้า coverage รวม** เช่น "ต้องถึง 80%" จะได้ test ที่เรียกฟังก์ชันแล้วไม่ assert อะไรเลย ให้วัด patch coverage แทน คือดูเฉพาะบรรทัดที่แก้ใน PR นั้น
- **เริ่มจาก getter setter หรือ model class** ตัวเลขขึ้นเร็วก็จริง แต่ไม่ได้ป้องกันอะไร
- **mock จนเหลือแต่ mock** ถ้า test ตัวหนึ่งต้อง mock 6 ตัว นั่นคือสัญญาณว่าโค้ดตรงนั้นรับผิดชอบหลายเรื่องเกินไป ไม่ใช่ปัญหาของ test
- **test ที่รันช้า** ถ้าชุด test ใช้เวลาเกินสองสามนาที คนจะเลิกรันในเครื่องตัวเอง แยก unit test กับ integration test ออกจากกันตั้งแต่แรก

## งานสัปดาห์แรกถ้าจะให้เห็นภาพ

ตั้ง framework + CI ให้เขียว หาฟังก์ชันคำนวณสัก 3 ตัวมาเขียน test ให้ครบทุกเคสรวมถึง edge case แล้วเอาเข้าที่ประชุมทีมให้ดูว่ารันแล้วเป็นยังไง จากนั้นค่อยคุยกฎสองข้อข้างบน

บอกได้ไหมครับว่าโปรเจกต์ใช้ภาษาอะไรกับ framework ไหน เดี๋ยวแนะนำ tool กับโครงไฟล์ให้ตรงกว่านี้ครับ
