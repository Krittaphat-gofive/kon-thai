เริ่มจากโค้ดที่กำลังจะแก้ครับ ไม่ใช่ไล่เขียนจากไฟล์แรกของโปรเจกต์

โปรเจกต์เก่าที่ไม่มี test เลย ถ้าตั้งเป้าว่า "จะเขียนให้ครบ" มันจะไม่จบ แล้วก็เลิกไปกลางทางเกือบทุกครั้ง วิธีที่ได้ผลกว่าคือทำให้ test ค่อย ๆ งอกตามงานที่ทำอยู่แล้ว

## ขั้นที่ 0 ทำให้รัน test ได้ก่อน

ก่อนจะคุยเรื่องเขียนอะไร ให้มี test ตัวแรกที่ผ่านใน CI ก่อน

- ตั้ง test project + test runner ให้ครบ
- เขียน test โง่ ๆ หนึ่งตัวที่ assert อะไรก็ได้ ให้มันผ่าน
- ต่อเข้า CI ให้ pipeline แดงจริงเวลา test พัง

ขั้นนี้ฟังดูไม่มีสาระ แต่เป็นจุดที่คนติดบ่อยที่สุด โปรเจกต์เก่ามักมี config แปลก ๆ ที่ทำให้ตั้ง test environment ยาก เคลียร์ตรงนี้ให้จบก่อน แล้วที่เหลือจะไหลเอง

## ขั้นที่ 1 เลือกเป้าแรก

เรียงตามความคุ้มค่า

1. **bug ที่เพิ่งเจอ** เขียน test ที่ fail ก่อน แล้วค่อยแก้ให้ผ่าน ได้ทั้ง test และความมั่นใจว่าแก้ถูกจริง
2. **business logic ที่คำนวณอะไรสักอย่าง** เช่น คิดราคา คิดภาษี ตรวจสิทธิ์ ตรวจเงื่อนไขวันลา พวกนี้ input ชัด output ชัด เขียน test ง่าย และพังแล้วเสียหายจริง
3. **โค้ดที่ทีมกลัวจะแตะ** ส่วนที่ทุกคนรู้ว่าแก้ทีไรพังทีนั้น ครอบ test ไว้จะได้กล้า refactor

ที่ไม่ควรเริ่ม คือ getter/setter, mapper, controller ที่แค่ส่งค่าต่อ เขียนแล้วตัวเลข coverage ขึ้นสวย แต่ไม่เคยจับ bug ได้เลย

## ขั้นที่ 2 ถ้าแตะไม่ได้เพราะ dependency พันกัน

ปัญหาคลาสสิกของ legacy คือฟังก์ชันเดียวเรียก DB เรียก API เรียก `DateTime.Now` ครบ จะ unit test ก็แยกไม่ออก

สองทางเลือก

- **ครอบด้วย integration test ก่อน** ยิงเข้าทั้ง flow เทียบ output กับของจริงที่ระบบคืนอยู่ตอนนี้ ไม่ต้องสนว่าถูกตามสเปกไหม เอาแค่ "ตอนนี้มันทำแบบนี้" เป็นตาข่ายกันพลาด แล้วค่อย refactor แยกส่วน logic ออกมาทีหลัง อันนี้คือ characterization test ในหนังสือ Working Effectively with Legacy Code
- **sprout method** ของใหม่ที่จะเขียน ให้แยกออกมาเป็น method หรือ class ใหม่ที่ test ได้ แล้วให้โค้ดเก่าเรียกเข้าไป ไม่ต้องรื้อของเดิม

อย่าเพิ่งรีบ refactor โค้ดเก่าเพื่อให้ test ง่าย ตอนที่ยังไม่มี test คุ้มกัน มันกลับหัวกลับหาง

## ขั้นที่ 3 ตั้งกฎทีม

กฎเหล็กข้อเดียวที่ทำให้มันไม่ตาย

> โค้ดใหม่ต้องมี test และโค้ดเก่าแตะตรงไหน เขียน test ตรงนั้น

วัดผลด้วย coverage ของ diff ใน PR ไม่ใช่ coverage รวมทั้งโปรเจกต์ ตัวเลขรวมจะขยับช้ามากจนทีมหมดกำลังใจ แต่ coverage ของ diff มันถึง 80% ได้ตั้งแต่ PR แรก

## ข้อควรระวัง

- **อย่า mock ทุกอย่าง** mock เยอะเกินไปทำให้ test ผูกกับวิธีเขียนโค้ด พอ refactor ทีเดียว test พังหมดทั้งที่ behavior เหมือนเดิม mock เฉพาะของที่ข้าม boundary จริง ๆ เช่น network, external API
- **อย่าตั้งเป้า coverage เป็นตัวเลข** เดี๋ยวจะได้ test ที่เรียกฟังก์ชันเฉย ๆ ไม่ assert อะไร
- **test ต้องเร็ว** ถ้าชุด unit test รันเกินสิบวินาที คนจะเลิกรันก่อน commit

ถ้าบอกมาว่าโปรเจกต์เป็นภาษาอะไร เฟรมเวิร์กไหน เดี๋ยวผมแนะนำ tooling กับโครงไฟล์ให้ละเอียดกว่านี้ได้ครับ
