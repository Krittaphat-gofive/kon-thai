# ความเห็นจาก Codex (1 ต.ค. 2569)

ถามครั้งเดียวผ่าน `codex exec` ล็อกอินด้วยบัญชี ChatGPT โมเดล gpt-6.1-sol
คำถามที่ส่งไปอยู่ท้ายไฟล์ ข้อความด้านล่างเป็นความเห็นของโมเดล ยังไม่ใช่ข้อเท็จจริงที่ตรวจแล้ว

---

ผมเห็นด้วยกับแนวทางสามชั้นครับ แต่จุดที่ควรแก้ก่อนคือ **แยก “ความชอบด้านสำนวน” ออกจาก “ข้อผิดพลาดทางภาษา”** ไม่อย่างนั้นโมเดลจะพยายามหลบคำจนภาษาแข็ง หรือเปลี่ยนความหมายทางเทคนิค

**1. จุดที่ยังฟังเหมือนภาษาแปลหรือ AI**

ตัวอย่างเหล่านี้เป็นข้อสังเกตด้านสำนวน ไม่ใช่หลักฐานว่าใครใช้ AI เขียน

| ลักษณะ | ก่อน → หลัง |
|---|---|
| ใช้นามธรรมแทนกริยา | “ทำการตรวจสอบความถูกต้องของข้อมูล” → “ตรวจว่าข้อมูลถูกต้องไหม” |
| คำขยายซ้อนจนอ่านเหนื่อย | “แนวทางนี้มีความยืดหยุ่นและมีประสิทธิภาพสูง” → “วิธีนี้เพิ่มเงื่อนไขได้ง่าย และลดจำนวน query” |
| ใช้ “โดย” ต่อประโยคยาว | “แก้ที่ service โดยเพิ่ม validation โดยตรวจ…” → “เพิ่ม validation ที่ service ก่อนบันทึก ให้ตรวจ…” |
| แปลโครงสร้าง *ensure that* | “ตรวจสอบให้แน่ใจว่าคุณได้ปิด connection” → “อย่าลืมปิด connection หลังใช้งาน” |
| แปล *in terms of* | “ในแง่ของประสิทธิภาพ query นี้…” → “query นี้ช้าตรงที่…” |
| อ้างกลับคลุมเครือ | “สิ่งนี้ช่วยแก้ปัญหาดังกล่าว” → “การเพิ่ม unique constraint ช่วยกันข้อมูลซ้ำ” |
| สรุปซ้ำโดยไม่เพิ่มสาระ | “โดยสรุป วิธีนี้ช่วยให้โค้ดมีคุณภาพดีขึ้น” → “วิธีนี้ทำให้ทดสอบส่วน validation แยกได้” |
| เกริ่นและชมเป็นสูตร | “เป็นคำถามที่ดีมาก เรามาเจาะลึกกัน” → “ต่างกันที่อายุของ object ครับ” |

อีกจุดคือ **จังหวะทั้งคำตอบ**: ทุกหัวข้อยาวเท่ากัน ทุกข้อมีคำอธิบายครบสูตร และปิดท้ายเสนอช่วยเสมอ อ่านแล้วเหมือนแม่แบบ แม้แต่ละประโยคจะถูกภาษาแล้วก็ตาม

**2. วิธีสั่งโมเดลที่ผมแนะนำ**

ยังบอกไม่ได้ว่าวิธีไหนดีที่สุดสำหรับ Claude รุ่นที่ใช้โดยไม่มีผลทดสอบ แต่ผมจะเริ่มแบบนี้

- **กฎสั้น + ตัวอย่างที่ดีหลายชนิดงาน**: แชตตอบสั้น อธิบายเทคนิค รายงานผลแก้บั๊ก และ PR description ตัวอย่างช่วยแสดงจังหวะที่กฎอธิบายยาก แนวทางใช้คำสั่งชัดเจนและตัวอย่างสอดคล้องกับ [คู่มือ prompting ของ OpenAI](https://developers.openai.com/api/docs/guides/prompt-engineering)
- **persona ใช้กำหนดระดับภาษา**: “senior dev ไทย” เป็นกรอบที่ดี แต่ไม่ได้รับประกันความเป็นธรรมชาติ ควรระบุเพิ่มว่าให้บอกเหตุผล ข้อจำกัด และสิ่งที่ยังไม่รู้
- **เขียน prompt ภาษาไทยได้**: เหมาะกับการอธิบายรสนิยมภาษาไทย แต่ผมไม่มีหลักฐานว่าดีกว่าภาษาอังกฤษเสมอ
- **hook เตือนเฉพาะหลักสำคัญ**: เช่น “ใช้สำนวนไทยที่อ่านคล่อง รักษาความหมายทางเทคนิค ไม่เติมผู้กระทำที่ต้นฉบับไม่ได้ระบุ” ไม่ต้องทวนรายการห้ามทั้งหมด
- สิ่งที่มักทำให้แข็งคือข้อห้ามจำนวนมาก การแทนคำแบบตายตัว และบังคับให้เติม “ก็/เลย/แล้ว” หรือ “ครับ” ตามตำแหน่ง

**3. วัดแบบประหยัดและพอเชื่อถือได้**

ใช้ linter เป็น **ตัวเตือน** แล้วให้คนประเมินเฉพาะตอนเปลี่ยน style หรือเปลี่ยนโมเดล

1. เก็บชุดทดสอบเดิมประมาณ 30–50 คำถาม ครอบคลุมชนิดงานและความยาว แยกบางข้อไว้โดยไม่ใช้ปรับ prompt
2. เทียบคำตอบสองเวอร์ชันโดยซ่อนชื่อและสลับลำดับ ให้ dev ไทยเลือก “อ่านเป็นธรรมชาติกว่า / เสมอ”
3. ให้คะแนนแยกสามเรื่อง: อ่านคล่องไหม ระดับภาษาเหมาะไหม และความหมายทางเทคนิคถูกไหม ห้ามรวมจนความถูกต้องถูกกลบ
4. ถ้าไหว ให้คนสองคนอ่านชุดย่อยเดียวกัน จะเห็นว่าข้อไหนเป็นความชอบส่วนตัว
5. รอบใช้งานปกติรัน linter แล้วสุ่มอ่านบางคำตอบ โดยสุ่มทั้งคำตอบที่ผ่านและไม่ผ่าน

ปรับ linter ให้ข้าม code block, inline code, ข้อความอ้าง และ error message พร้อมรายงานแยกตามความยาวคำตอบ จำนวนคำต้องห้ามลดลงอาจเกิดจากคำตอบสั้นลงเฉย ๆ

**อย่าใช้คะแนน “ดูเป็น AI” เป็นเป้าหมายหลัก** ให้ใช้ “คนในทีมอ่านเข้าใจและรู้สึกเป็นธรรมชาติ” จะประเมินตรงงานกว่า

**4. กฎใน style ที่ควรแก้**

- **“ถูกใช้กับเรื่องไม่ดี” เหมารวมเกินไป**  
  “ถูกเลือก”, “ถูกจัดเก็บ”, “ถูกเรียกใช้” ใช้ได้ ไม่จำเป็นต้องสื่อเรื่องร้าย แก้เป็น “หลีกเลี่ยงรูปถูกกระทำเมื่อทำให้ประโยคอ้อมหรืออ่านสะดุด”

- **ห้ามเติมผู้กระทำเพื่อแก้ passive**  
  จาก “component ถูก destroy” เป็น “Angular destroy component” ต้องรู้ก่อนว่า Angular เป็นผู้ทำจริง ถ้าไม่รู้ ใช้ “component นี้ destroy ไปแล้ว” ตามบริบท หรือเรียบเรียงใหม่โดยรักษาข้อมูลเดิม

- **คู่แทนสำนวนบางคู่เปลี่ยนความหมาย**  
  “กฎทอง” กับ “กฎเหล็ก” น้ำหนักต่างกัน และ “ช่วยได้มากที่สุด” เพิ่มการเปรียบเทียบที่ต้นฉบับไม่มี ควรเขียนความหมายตามบริบท เช่น “หลักที่ควรจำ” หรือ “ตารางนี้ช่วยให้เลือกวิธีได้ง่ายขึ้น”

- **อย่าบังคับคำอังกฤษเป็นตัวพิมพ์เล็กทั้งหมด**  
  คงรูปมาตรฐาน เช่น API, SQL, HTTP, Git และรูปชื่อผลิตภัณฑ์ รวมทั้งตัวพิมพ์ของ identifier

- **“คุณ” และ “มัน” ไม่ผิดโดยตัวเอง**  
  ละเมื่อไม่จำเป็น แต่เก็บเมื่อช่วยแยกผู้กระทำหรือทำให้น้ำเสียงตรงบริบท “ตัวนี้/แบบนี้” ถ้าใช้ถี่ก็คลุมเครือได้เหมือนกัน

- **“อย่างไรก็ตาม / หาก / ส่งผลให้” ไม่ต้องห้ามเด็ดขาด**  
  ใช้ “แต่ / ถ้า / ทำให้” เป็นค่าเริ่มต้นได้ ส่วนเอกสารบางชนิดใช้คำเดิมแล้วเหมาะกว่า

- **กฎเครื่องหมายควรมีขอบเขต**  
  เลี่ยง em dash และจุดท้ายประโยคได้ตามรสนิยมนี้ แต่ยกเว้นข้อความต้นฉบับ โค้ด และรูปแบบเอกสารที่จำเป็น

- **“ก็ / เลย / แล้ว” และการยกเงื่อนไขขึ้นก่อนควรเป็นทางเลือก**  
  บางประโยคตรง ๆ อย่าง “DbContext ใช้พร้อมกันสองงานไม่ได้” อ่านดีกว่า “ตัว DbContext นี่…”

- **ตัวอย่างมีข้อสรุปทางเทคนิคเกินข้อมูล**  
  `NullReferenceException` อาจเกิดจากการเรียกสมาชิกหรือเมธอดผ่านค่า `null` ไม่ใช่เฉพาะ property และยังชี้ `FindAsync` ว่าน่าสงสัยที่สุดไม่ได้ถ้าไม่เห็นโค้ด ส่วน “Promise เริ่มทันทีที่สร้าง” ควรระบุว่า executor ของ `new Promise(...)` ทำงานทันที เพื่อไม่ให้เข้าใจว่างานทุกชนิดเริ่มตอนสร้าง Promise

ผมจะเพิ่มกฎนี้ไว้เหนือรายการแก้สำนวน:

> รักษาความหมาย ความแน่นอน และผู้กระทำตามข้อมูลเดิม การเกลาภาษาต้องไม่เพิ่มข้อเท็จจริง ถ้ากฎด้านสำนวนทำให้ความหมายเปลี่ยน ให้รักษาความหมายก่อน

**5. ภาษาไทยของ ChatGPT มาจากข้อมูลแบบไหน**

OpenAI เปิดเผยแหล่งข้อมูลโดยรวมสามกลุ่ม: ข้อมูลสาธารณะบนอินเทอร์เน็ต ข้อมูลที่เข้าถึงผ่านพันธมิตร และข้อมูลที่ผู้ใช้ ผู้ฝึก และนักวิจัยให้หรือสร้างขึ้น ตาม [คำอธิบายการพัฒนาโมเดลของ OpenAI](https://openai.com/policies/how-chatgpt-and-our-foundation-models-are-developed/)

**ผมไม่ทราบรายละเอียดชุดข้อมูลภาษาไทยหรือสัดส่วนของแต่ละแหล่ง** จึงยืนยันไม่ได้ว่าภาษาไทยมาจากเว็บไซต์ไหน หนังสือไหน งานแปลมากแค่ไหน หรือผ่านผู้ตรวจภาษาไทยอย่างไร และสำนวนที่ฟังเหมือนแปลก็ยังไม่พอให้สรุปว่าเกิดจากข้อมูลฝึกประเภทใด

## คำถามที่ส่งไป

ขอความเห็นในฐานะคนที่เขียนภาษาไทยเก่ง เรื่องการทำให้ AI เขียนภาษาไทยเป็นธรรมชาติ

## งานที่ทำอยู่

กำลังตั้งค่า Claude Code ให้ตอบภาษาไทยเหมือน senior developer คนไทยอธิบายงานให้เพื่อนร่วมทีมฟัง ภาษากึ่งทางการ แทนตัวเองว่าผม ลงท้ายครับ ทำไว้สามชั้น
1. output style คือ system prompt ที่ส่งไปทุกคำตอบ (เนื้อหาเต็มอยู่ด้านล่าง)
2. hook ที่แทรกข้อความเตือนสั้น ๆ ทุกครั้งที่ผู้ใช้พิมพ์ภาษาไทย
3. skill สำหรับเกลางานเขียนยาว ที่รัน linter หาร่องรอยภาษาแปลก่อนแล้วค่อยแก้

ตอนยังไม่มี style คำตอบภาษาไทยของ Claude มีปัญหาแบบนี้ (นับจาก 20 คำถาม)
- em dash (—) 143 ครั้ง
- passive "ถูก" กับเรื่องปกติ 28 ครั้ง เช่น "view นั้นถูก check ไปแล้ว"
- "มัน" แทน it 19 ครั้ง
- แปลสำนวนอังกฤษตรงตัว เช่น กฎทอง (golden rule), ยาแก้ปวด (band-aid), โรย setTimeout (sprinkle), ตัวเปลี่ยนเกม (game changer)
- สะกดทับศัพท์ไม่ตรงราชบัณฑิตฯ เช่น เช็ค เวอร์ชั่น
- ใส่ครับไม่สม่ำเสมอ และใช้ "คุณ / ของคุณ" แบบแปลจาก you / your

พอใส่ style แล้ว จุดพวกนี้แทบหายหมด แต่ linter นับได้แค่สิ่งที่เรากำหนดไว้เอง เลยอยากได้มุมมองจากภายนอก

## คำถาม

1. นอกจากรายการข้างบน ภาษาไทยของ AI มักแปลกตรงไหนอีกบ้าง ที่คนไทยอ่านแล้วรู้ว่าแปลมา หรือรู้ว่าเป็น AI เขียน ขอเป็นตัวอย่างก่อน→หลังในบริบทงาน dev
2. ถ้าจะสั่งโมเดลให้เขียนภาษาไทยเป็นธรรมชาติ วิธีไหนได้ผลที่สุด เช่น กฎ ตัวอย่าง persona หรือเขียน prompt เป็นภาษาไทย แล้วอะไรที่มักทำให้แย่ลง
3. ถ้าจะวัดว่าภาษาไทยเป็นธรรมชาติแค่ไหน แบบประหยัดและเชื่อถือได้ ควรวัดยังไง ไม่อยากต้องเรียกโมเดลอื่นมาตัดสินทุกครั้งเพราะเปลืองเงิน
4. ช่วยอ่าน output style ด้านล่าง แล้วบอกว่ามีกฎข้อไหนผิด ขาด หรือแก้เกินเหตุจนภาษาแข็ง
5. ภาษาไทยของ ChatGPT มาจากข้อมูลแบบไหน ถ้าไม่รู้แน่ชัดให้บอกว่าไม่รู้ ไม่ต้องเดา

ตอบเป็นภาษาไทย กระชับ เป็นข้อ ๆ เรื่องไหนไม่แน่ใจให้บอกตรง ๆ
