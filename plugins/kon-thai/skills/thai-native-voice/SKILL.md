# thai-native-voice

รอบขัดเกลาภาษาไทยให้ฟังเหมือน senior dev คนไทยเขียนเอง แยกจากรอบร่าง เพราะงานวิจัยด้านแปลภาษาพบว่าสั่งแค่ "เขียนให้เป็นธรรมชาติ" ได้ผลไม่แน่นอน แต่การขัดเกลาเป็นอีกรอบช่วยได้สม่ำเสมอ และ Claude มักมองไม่เห็นร่องรอยภาษาแปลในงานของตัวเอง ต้องมี linter ช่วยชี้

หลักข้อแรก: เกลาแล้ว ความหมาย ระดับความมั่นใจ และผู้กระทำต้องเท่าเดิม ถ้าต้นฉบับไม่ได้บอกว่าใครทำหรือเกิดจากอะไร ก็ไม่ต้องเติม ถ้ากฎเรื่องสำนวนข้อไหนทำให้ความหมายเปลี่ยน ให้รักษาความหมายไว้ก่อน

## ขั้นตอน

1. ร่างเนื้อหาให้ครบก่อน หรือใช้ข้อความที่ผู้ใช้ให้มา
2. รัน linter กับร่าง โดยส่งข้อความเข้า stdin:
   ```bash
   python "<base directory ของ skill นี้>/scripts/thai_lint.py" - <<'EOF'
   ...ร่าง...
   EOF
   ```
   ถ้าร่างอยู่ในไฟล์แล้ว ส่ง path ของไฟล์แทน `-` ได้เลย ถ้าตอนนี้แทนตัวเองว่าดิฉันและลงท้ายค่ะ ให้เติม `--persona kha` (ค่าเริ่มต้นคือผม/ครับ)
   ถ้าเครื่องไม่มี python ให้ข้ามขั้นนี้ แล้วไล่ตรวจเองตามตารางข้างล่างกับ [references/anti-patterns.md](references/anti-patterns.md) แทน
3. ไล่ทุกจุดที่ linter จับ แล้วตัดสินทีละจุด linter จับแบบหยาบ เช่น "ถูก" ที่แปลว่าถูกต้อง แต่ละจุดมีประเภทกำกับไว้
   - `แปล`: ร่องรอยภาษาแปล แก้ตามตารางข้างล่าง หรือเปิด [references/anti-patterns.md](references/anti-patterns.md)
   - `ทางการ`: ภาษาราชการ ในแชตเปลี่ยนเป็นคำที่พูดกันจริง ถ้าเป็นจดหมายหรือประกาศใช้คำเดิมได้
   - `บุคคล`: ผิด persona เช่น persona ผม/ครับ แต่ใช้ "ค่ะ" หรือ persona ดิฉัน/ค่ะ แต่เขียน "นะค่ะ" (ต้องเป็น "นะคะ") แก้ให้ตรง persona ที่ใช้อยู่
   - `house`: ตัวสะกด ไม้ยมก การเว้นวรรค ไม่ใช่ร่องรอยภาษาแปล คนไทยเองก็เขียนต่างกันบ่อย แก้ให้ตรงกับแบบที่ชุดนี้ใช้
4. อ่านทวนทั้งชิ้นหาสิ่งที่ linter จับไม่ได้
   - ข้อสรุปอยู่ต้นเรื่องไหม
   - มีสำนวนอังกฤษแปลตรงตัวที่ linter ไม่รู้จักไหม
   - มีคำกว้าง ๆ อย่าง "ยืดหยุ่น" หรือ "มีประสิทธิภาพ" ที่ควรบอกผลจริงแทนไหม
   - ระดับภาษาตรงกับชนิดงานไหม
5. รัน linter ซ้ำ จนจุดที่เหลือเป็นจุดที่ตั้งใจคงไว้
6. ถ้าผู้ใช้ให้ข้อความมาเกลา ส่งฉบับเกลาแล้วก่อน ตามด้วยหัวข้อ `## สิ่งที่แก้` เป็น bullet ไม่เกิน 5 ข้อ ข้อละบรรทัดเดียว สรุปนี้ก็เป็นภาษาไทยที่คนจะอ่าน เลยใช้กฎเดียวกับตัวงาน (ไม่มี em dash ไม่มี ถูก กับเรื่องปกติ)

## จุดที่ต้องแก้บ่อยที่สุด

ตารางนี้เป็นตัวอย่าง ไม่ใช่คู่คำที่ต้องแทนทุกครั้ง ดูความหมายในบริบทก่อนเสมอ

| ที่เจอ | แก้เป็น |
|---|---|
| em dash (—) | เว้นวรรค ขึ้นบรรทัดใหม่ ใช้ : หรือวงเล็บ |
| ถูก + กริยา กับเรื่องปกติ: "ข้อมูลยังไม่ถูกเก็บ" | เขียนแบบไม่มีประธาน: "ยังไม่ได้เก็บข้อมูล" |
| ถูก + กริยา ที่รู้แน่ว่าใครทำ: "method นี้ถูกแปลงเป็น struct" | ยกผู้ทำขึ้นมา: "compiler แปลง method นี้เป็น struct" |
| มันเป็น… / มันคือ…: "มันเป็นอะไรที่ดูแลยาก" | พูดถึงตัวเรื่อง: "ส่วนนี้ดูแลยาก" |
| มัน ที่ไม่ชัดว่าหมายถึงอะไร | เรียกชื่อสิ่งนั้น ส่วน มัน ที่ชัดอยู่แล้วคงไว้ได้ |
| ของคุณ: "method ของคุณ" | ละไป: "method นั้น" |
| ตรวจสอบให้แน่ใจว่า…: "ตรวจสอบให้แน่ใจว่าปิด connection" | พูดตรง ๆ: "อย่าลืมปิด connection" |
| สำนวนแปล: กฎทอง, ยาแก้ปวด, โรย, ตัวเปลี่ยนเกม | เขียนความหมายในบริบทนั้น เช่น "กฎข้อเดียวที่ห้ามพลาด", "แก้ที่ปลายเหตุ", "ใส่…ไปทั่ว" |
| ทำการ… / มีความ… | ใช้กริยาตรง ๆ: ติดตั้ง, ซับซ้อน |
| house style: "จริงๆ", เช็ค, อัพเดท, เวอร์ชั่น | "จริง ๆ", เช็ก, อัปเดต, เวอร์ชัน |

## ระดับภาษาตามชนิดงาน

- แชต: กึ่งทางการ ใช้สรรพนามกับคำลงท้ายตาม output style ที่เปิดอยู่ (ผม/ครับ หรือ ดิฉัน/ค่ะ) ใส่คำลงท้ายที่ประโยคแรก ถามกลับเฉพาะตอนที่ต้องการข้อมูลจากผู้ใช้
- README, คู่มือ, PR description, commit message: ไม่มีคำลงท้าย ไม่มีสรรพนาม ประโยคสั้นและตรงประเด็น
- จดหมายหรือประกาศถึงลูกค้า: ใช้แบบแผนจดหมายไทยได้ (เรียน…, ขอแสดงความนับถือ) คำอย่าง "หาก" หรือ "ดำเนินการ" ก็ใช้ได้
- Slack หรือ LINE ถึงคนในทีม: เป็นกันเองได้

## ศัพท์เทคนิค

- คำที่ dev ไทยพูดเป็นภาษาอังกฤษอยู่แล้ว เขียนเป็นอังกฤษ คำทั่วไปตัวพิมพ์เล็ก เช่น deploy, merge, query ตัวย่อและชื่อเฉพาะคงรูปเดิม เช่น API, SQL, Git
- คำทับศัพท์สะกดตามราชบัณฑิตยสถาน ถ้าในเครื่องมี skill หรือตารางทับศัพท์ของทีมอยู่แล้ว ให้ใช้ตารางนั้นก่อน
- เว้นวรรคระหว่างคำไทยกับคำอังกฤษหรือตัวเลข กฎเว้นวรรคทั้งหมดอยู่ใน [references/spacing-punctuation.md](references/spacing-punctuation.md)
- โค้ด ชื่อตัวแปร คำสั่ง error message และข้อความที่ยกมาจากต้นฉบับ คงไว้ตามเดิมทุกตัวอักษร

## ความผิดพลาดที่พบบ่อยตอนเกลา

- เติมผู้กระทำหรือสาเหตุที่ต้นฉบับไม่ได้บอก เพื่อแก้ passive ให้เขียนแบบไม่มีประธานแทน
- จับคู่คำแทนแบบตายตัวจนน้ำหนักความหมายเปลี่ยน เช่น เปลี่ยน "กฎทอง" เป็น "กฎเหล็ก" ทุกที่
- คง em dash ไว้เพราะคิดว่าไม่ใช่ปัญหา dev ไทยแทบไม่ใช้เครื่องหมายนี้
- สลับคำทีละคำ แต่โครงประโยคยังเป็นภาษาอังกฤษ ต้องเรียงประโยคใหม่ทั้งประโยค
- เปลี่ยน "ถูก" เป็น "ได้รับ" ทั้งที่ "ได้รับ" ก็เป็นร่องรอยงานแปลเหมือนกัน
- ลบ "สามารถ" หรือ "ไม่สามารถ…ได้" ทุกคำ ข่าวไอทีที่คนไทยเขียนใช้ "สามารถ" ถี่กว่า Claude เสียอีก
- แปลศัพท์ dev เป็นไทย เช่น merge เป็น "ผสาน"
- เปลี่ยนเนื้อหาหรือโค้ดระหว่างเกลา
